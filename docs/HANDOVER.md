このリポジトリを、ユーザーの Claude のプロジェクトと、別のアカウントの Claude のプロジェクトの
両方から同時に開発するための手順と、今の状況です（2026-10-14 時点）。
作業のルールは [CLAUDE.md](../CLAUDE.md) の「共同開発」、作業は [TODO.md](../TODO.md) にあります。

Claude のプロジェクトのメモ（MEMORY）は、そのプロジェクトの中からしか見えません。
**両方の Claude が知っておくべきことは、このファイル・CLAUDE.md・TODO.md に書いてコミットします。**

## 1. GitHub で招待する（ユーザーがやる）

ytani01/bganalyzer の Settings → Collaborators → Add people で相手のアカウントを招待する（Write 権限）。
相手が招待を承認すると、ブランチの push と PR のマージができるようになる。

## 2. 相手側でプロジェクトを作る（共同開発者がやる）

1. claude.ai で新しいプロジェクトを作る。名前と説明の例:
   - 名前: `BACKGAMMONボード分析`
   - 説明: `バックギャモンボードの写真を読み込み盤面を分析し、どちらが有利か判定する`
2. 自分の GitHub アカウントを Claude につなぐ（https://claude.ai/connect-github ）。
3. プロジェクトの設定でリポジトリ `ytani01/bganalyzer` を追加する。
4. 「3. プロジェクト指示」の文面をプロジェクトの指示に貼る。
5. プロジェクトのチャットに「4. 最初のメッセージ」を送る。

ユーザーのプロジェクトの指示にも、同じ文面が入っていることを確かめる。

## 3. プロジェクト指示（両方のプロジェクトに貼る）

```text
- ユーザーとのやりとりは日本語で行う。
- リポジトリ ytani01/bganalyzer は別アカウントの Claude プロジェクトと共同で開発している。
  作業する前に main を pull し、リポジトリ直下の CLAUDE.md（特に「共同開発」）と docs/HANDOVER.md に従う。
- 自動マージ: スレッドが作った PR は、マージ直前に最新 main を取り込み、
  GitHub Actions の test が通り（文書だけの PR では test は走らない。TODO-064）、差分を見直して問題がなければ、ユーザーの確認を待たずにそのスレッド自身が
  マージする。マージしたことは一言報告する。テスト失敗・未検証の重要事項・判断が必要な点・
  相手の変更とのぶつかりがある場合はマージせず報告する。
- 方針や進み具合が変わったら、プロジェクトのメモだけでなく docs/HANDOVER.md か TODO.md にも書いてコミットする。
```

## 4. 最初のメッセージ（相手のプロジェクトのチャットに送る）

```text
このプロジェクトは ytani01/bganalyzer を別アカウントのプロジェクトと共同で開発します。
リポジトリの CLAUDE.md、docs/HANDOVER.md、TODO.md を読み、「5. 今の状況」をプロジェクトのメモに保存してください。
そのあと、自分が担当できそうな作業を TODO.md から挙げてください。
```

## 5. 今の状況

- **目標:** スマホで撮った実物の盤の写真 → 盤面認識 → GNU Backgammon で解析（勝率・ギャモン率・ピップ数）→ PWA で表示。
- **計画と進み具合:** 1 盤面認識（済）、2 gnubg 解析・サーバー側（済）、3 手動修正付きの PWA（済）、
  4 実写真での調整（済。斜めの写真は警告で対応）。
- **四隅の初期値（TODO-010、2026-10-13。TODO-028 で 2026-10-15 に作り直し）:** 写真を読み込むと `/find-corners`（`recognizer/corners.py`）が
  盤の縁の直線と三角形の並びから四隅を推定し、PWA はそれを初期値に出す（ユーザーはドラッグで直す）。見つからなければ
  画像の内側の長方形から始まる。当たり具合は recognizer/README.md の「四隅の推定」（全 24 枚で 3.6% 以内が 15 枚、見つからないものなし）。
- **ダイスの自動入力（TODO-015、2026-10-13）:** フィールドの 2 つのダイスが自信を持って読めたときだけ、`/analyze-photo` が
  `dice_read` を返し、PWA がダイスの目の初期値にする（`recognizer/dice.py`。当たり具合は recognizer/README.md の「ダイス」）。
- **キューブ判断（TODO-025、2026-10-13）:** ダイスが無いと gnubg のキューブ判断（マネーゲーム、ジャコビーあり・ビーバーなし）を出す。
  gnubg の Python モジュールにキューブ判断の関数がないので、解析の子プロセスで `hint` コマンドの表示を読む（`analyzer/engine.py`）。
  キューブが片側にあってダイスが無ければ「その側がダブルされた」とみなしてテイク／パスを判定する。写真からはキューブの場所だけ読み
  （`recognizer/cube.py`）、数字は読まない（片側なら 2 とし、画面で直す）。
- **認識精度（24ポイント中）:** 元の写真で photo2 23、photo3 24、photo4 24、スクショ2枚 24、photo1（斜め撮影）14（photo1 は 2026-10-13 に顔が写っていたためファイルも履歴も削除した）。
  PWA は長辺 2560px を超える写真を 2048px に縮めて送る。その写真では photo1 18、photo2 23、photo3 24、photo4 23
  （TODO-004 で直した。完了済み）。斜めすぎる写真（40° 超）にはアプリで撮り直しを勧める警告を出す。斜めの写真の精度改善は、ユーザーが「一旦これで十分」として TODO-005 を完了にした。
- **ユーザーの盤:** クラフト紙色の盤面、赤と紺の三角形、白い枠。駒はえんじ色と紫。えんじ色の駒と赤い三角形は
  色がほぼ同じ（Lab で差 ~8）で、色だけでは区別できない。斜めの写真が一番の弱点なので、真上から撮ってもらう。
- **公開先は自宅の Raspberry Pi + Tailscale Funnel**（`https://<Pi>.<tailnet>.ts.net/bg/`、無料・ドメイン不要。同じ Pi で別のアプリも別のパスで公開する予定があるので、アプリはパスの下でも動くようにしてある）（手順は [raspi.md](raspi.md)）。2026-10-12 にユーザーが Pi で動くことを確かめた（TODO-002 完了）。
  ホーム画面への追加には HTTPS が必要。サーバーレス関数は不可、ワーカー1つで常駐。
- **Docker は使わない**（2026-10-15、TODO-056）。Pi も uv で入れ、systemd のユーザー unit（`bganalyzer.service`）で常駐させる。

  `tools/pi_ui_check.py` は `window.BgApp` を使う（`BG_URL`・`BG_CHROMIUM` で Pi 以外でも動く）。
