# 盤面認識プロトタイプ（ステップ1）

スマホで撮った実ボードの写真から、各ポイントの駒の数と色、バーの駒、上がった駒を読み取り、
GNU Backgammon にそのまま渡せる **Position ID** を出します。

## 使い方

```
uv run python board.py <写真> --corners x1,y1,x2,y2,x3,y3,x4,y4 --home left|right|auto [--bottom-colour 0|1] [--debug 出力先]
```

- `--corners`: 盤の遊戯面（左右のフィールド＋バー、枠の内側）の四隅。手前側プレイヤーから見て 左上, 右上, 右下, 左下 の順。
  ざっくりで構いません（盤の縁と三角形の先端で自動補正します）。アプリでは下の「四隅の推定」で初期値を置き、ユーザーがドラッグで直します。
- `--home`: 手前プレイヤーのホームボードが左右どちらか。`auto` なら駒の並びから推測する（下の「ホームボードの推測」）。
- `--bottom-colour`: 手前プレイヤーの駒の色（0 = 暗い方、1 = 明るい方）。アプリでは「自分の色」を選んでもらいます。
- 出力: 盤面のアスキー表示と JSON（points, bar, off, pips, position_id_white_on_roll / black_on_roll, errors）。
  White = 手前プレイヤー。駒が15個でないときは `errors` に出るので、アプリで手修正を促せます。

依存: Python 3, numpy, opencv-python-headless。

## 仕組み

1. 四隅 → 真上から見た盤への射影変換。
2. 盤の縁を直線で検出して補正し、さらに **三角形の先端と辺** に合わせて射影変換を推定し直す。
   三角形は盤面に印刷されているので、斜め撮影でも枠の高さによるズレを受けない。
3. 盤の地の色・三角形2色・枠の色を自動で学習。
4. 駒は円として検出し、「縁がはっきりした円」「中が単色」「そこが空いていた場合の色（地・三角形、縁の近くなら枠）と違う」で選別。
   山の途中や、2 個以上の山と枠の間にある弱い円（白い三角形の上の白い駒、茶色い三角形の上の茶色い駒など）も駒とみなす。
   三角形の辺がはっきり見える位置の円は捨て、枠から続けて辺が隠れている列には、円が出なくても駒を足す（TODO-027）。
   駒の山に入った円だけで2色を学び（ダイスカップなどに色の片方を取られないように）、反射で白っぽく写った色付きの駒（赤がピンクに見える等）は色味で色付きの側に戻す。
5. 列の位置を、見つかった駒の並びに合わせて微調整する（三角形が見えにくい盤やアプリ画面向け）。
6. ポイントごとに、根元から連続して、まっすぐ積まれた駒を数える（途中の1〜2個の見落としは補う。アプリのように駒が重なった山は重なりの間隔で数える）。
   横にずれて重なった丸（ダイスカップ）は山とみなさない。1個だけの駒は、はっきりした円のときだけ数える。
   上がった駒 = 15 −（盤上＋バー）。

### CPU で変わらない読み取り（2026-10-15、TODO-046、recognizer 0.14.0）

0.13.1 までは、同じ写真でも x86_64 と Raspberry Pi（aarch64）で読みが違った（GitHub の arm64 の実行機で 24 枚中 4 枚、
SIMD を SSE2 までに落とした x86_64 で 7 枚）。原因は浮動小数点の端数の扱いで、どれも最後の 1 ビットほどの違いが、しきい値・丸め・最大値の選択で
大きな違いになっていた:

- OpenCV の浮動小数点の処理（`warpPerspective` の座標、`GaussianBlur`・`Sobel` の float 版、`kmeans`、`getPerspectiveTransform`・`findHomography`）は、
  使う命令（AVX2・NEON、aarch64 の積和の一体化 FMA）で端数が変わる。OpenCV 5 の `warpPerspective` は 8 ビットの画像でも 805 画素が 1 違った
- NumPy の BLAS・LAPACK（`@`・`inv`・`polyfit`・1 次元の `norm`）は足す順番が CPU で違い、`cos`・`sin`・`arctan2`・`hypot`・`exp`・`interp` も最後の桁が違いうる

そこで読み取り（`board.py`・`dice.py`・`cube.py`）を、どこでも同じになる計算だけで組み直した（`exact.py`）:

- 画像は 8 ビットか整数のまま扱う（`cvtColor`・`GaussianBlur` は 8 ビット、`Sobel` は 16 ビット整数、範囲の引き伸ばし・箱の和は NumPy の整数）
- 斜めから真上への写し直しは、元の位置を float64 の 1 演算ずつで出して 1/32 画素に切り、`cv2.remap` の整数の補間で混ぜる（`exact.warp`）
- 射影変換・直線・逆行列は Python の float か NumPy の 1 演算ずつ（足し算の順番は NumPy が決める）で解く。RANSAC は、外れた点を除いて解き直す最小二乗に替えた
- k-means は整数で（`exact.kmeans`。四隅の推定で TODO-028 がしたのと同じ）。色相の差は `arctan2` でなく余弦で比べる
- ダイスの外接長方形は `cv2.minAreaRect` でなく `exact.min_area_rect`（arm64 の NEON_DOTPROD などを使うと、OpenCV のものは別の箱を返した）
- 段の間で渡す値（四隅、盤の幅、列の位置）は細かい格子に丸め、万一の 1 ビットの違いが次の段に届かないようにした

確かめ方: `recognize(trace=...)` が各段の値のハッシュを残し、`trace_cpu.py check` が全サンプルの各段とを `cpu_reference.json` と比べる。
AVX-512 のあるなし（このクラウド環境）でも同じ。GitHub Actions の `cpu-match` が x86_64 と arm64 の両方でこれを走らせていたが、
TODO-064 でやめた（`accuracy` と全サンプルの読み取りが重なるため）。今は `test` が 1 サンプルだけ x86_64 と arm64 で比べる。
recognizer を変えた PR は `uv run python recognizer/trace_cpu.py --update` で基準も書き直す。

決めたこと（2026-10-14、ユーザー）どおり、一致を精度より優先した。精度の基準は 529 → 518 になった:
case-dice 19 → 23、set-cube-dice 15 → 17、dark-homeleft 20 → 21、tavli-burl 23 → 24、tv-vegas-open 23 → 24 と良くなり、
leather-cups 20 → 11（列が 1 つずれる。前から Pi では 9 だった）、travel-case 21 → 16、tavli-red-white 24 → 22、screen2 24 → 22、nardy-midgame 18 → 17、photo4 24 → 23 と悪くなった。
画素が 1/64 画素ずれるだけで合計が 8 ポイント動くほど、今の読み方は細かい違いに敏感で（TODO-028 でも同じことが分かっている）、悪くなったものの多くはこの揺れの範囲。
種や値を選んで精度を合わせることはしない（TODO-028 と同じ）。また、駒の山の途中で円が見つからなかった駒をキューブと取り違えないよう、
山の 2 つの駒の間にある正方形はキューブとしない（`cube.py`）。読み取りの時間は 1 枚あたり 0.5〜1.3 秒（10〜20%）増えた（このクラウド環境）。

## 四隅の推定（`corners.py`）

写真を読み込んだ直後に、アプリが四隅の初期値として出すための推定。`find_corners(img)` が
左上・右上・右下・左下（画像の画素）を返し、盤が見つからなければ `None`（アプリは画像の内側に余白をとった長方形から始める）。
`find_corners(img, progress=f)` とすると、探す段階が終わるたびに `f(段階, 見つけたもの)` を画像の画素で呼ぶ
（`edges` 横の縁の候補 → `uprights` 縦の縁の候補 → `candidates` 盤らしい四角形の候補 → `corners`。結果は変わらない。アプリの途中経過の表示に使う）。
コマンドラインでは `uv run python corners.py <写真>...`。全サンプルでの当たり具合は `uv run python recognizer/check_corners.py`
（`--app` でアプリと同じく縮めた写真）。

ユーザーが直したあとの「もう一度検出」（TODO-068）では、`find_corners(img, fixed=[左上, 右上, 右下, 左下], crop=(x0, y0, x1, y1))` とする。
`fixed` はユーザーが置いた隅（置いていない隅は `None`）で、そのまま返る。候補の四角形のうち、その隅から探す範囲（`crop` が無ければ写真全体）の長辺の 5% より離れたものは使わない
（使うと、固定した隅に合わせて歪んだ四角形が点数で勝つ）。`crop` はユーザーが囲んだ範囲で、その中だけを探し、遊戯面は範囲の幅の 5 割・高さの 4 割以上とする。
`check_corners.py --fix N`（最初の N 個の隅を正解に置く）と `--crop`（正解の外接矩形と 15% の余白）で当たり具合を測れる（値は `archives/agents/TODO-068/README.md`）。

recognizer 0.16.0（TODO-028）で、三角形の色の領域を探す作り方をやめ、**盤の縁の直線から作り直した**。
0.14.0 までの作り方（色を k-means で 8 つに分けて細長い三角形の領域を探す）は、分け方が初期値で大きく変わり、
三角形の見えない盤や強い斜めで見つからなかった（下の表の「0.14.0 まで」）。

1. 長辺 800px に縮める（`pyrDown` と `INTER_LINEAR_EXACT`、整数だけ）。Lab の 3 つのチャンネルの勾配（8 ビットでぼかし、16 ビットの Sobel）を足す。
2. **奥と手前の縁の候補:** 上下に明暗が変わる画素で、ほぼ水平（傾き 0.3 まで）な直線のハフ変換（整数）の強い順に 6 本。
3. **左右の縁の候補:** 奥と手前の候補の組ごとに、その間の行の 45% 以上で縁の画素が乗る、ほぼ垂直な直線を 8 本。
   三角形の辺は盤の高さの半分も続かないので落ち、枠・バー・ケースの縁が残る。同じ縁を別の傾きで数えないよう、帯の真ん中での位置で間引く。
4. 組み合わせた四角形（盤の縦横比 0.8〜2.2）を真上から見た形（104x80）にして、構造の点数で選ぶ:
   - 24 個のポイントそれぞれで、フィールドの地の色からの離れ具合と三角形の形の相関（バーの幅は 0〜18% を試す）
   - 奥と手前の先端の間の帯が、両フィールドの端まで地の色か（枠やケースを取り込んだ四角形はここで点を落とす）
5. 点数の高い 12 個は、**各辺をその近く（外へ 6%、内へ 5%）の、いちばん内側の強い縁に動かした形**も作り、208x160 で点数をつけ直して、いちばん高いものを答える。
   枠には段や面取りがあり、外側の縁の方が強いことが多い。点数が 0.15 に届かなければ見つからなかったことにする。

すべて整数と、どの CPU でも同じに丸まる計算（`exact.py`）なので、x86_64 と Raspberry Pi で四隅は同じになる（`trace_cpu.py` が全サンプルの四隅も比べる）。
時間はこのクラウド環境で 1 枚 1.0〜1.8 秒（0.14.0 までは 0.2〜1.9 秒）。

## ダイス（`dice.py`、TODO-015）

`recognize()` の `info["dice"]` に、フィールドに転がっているダイスを入れる: `values`（読めた 2 つの目、大きい方から。
自信がないときは `null`）と `dice`（見つけたダイスごとの位置・大きさ・目・`sure`・`on_bar`）。アプリは `values` を
ダイスの目の初期値にする。

1. 盤を写真の解像度で真上から見た形に写し直す（駒の直径が 120px になるまで。ダイスの目は数画素しかない）。
2. 明るさのしきい値を 16〜248 まで 8 ずつ変え、明るい側・暗い側それぞれで、駒の直径の 0.28〜1.1 倍の大きさの
   正方形（四隅があって外接長方形をほぼ埋める。駒の円は埋めない）を体として集める。
3. 体の中で、まわりの面より暗い（明るい）小さな丸を目とする。面との差の取り方を 6 通り（局所的な差・明るさの段階 ×
   切る位置 3 つ）試し、目の並びが体の向きにそろったダイスの面（1〜6）になっているものを「読み」とする。
   暗い目と明るい目の両方で読めた体は捨てる。駒の真ん中のくぼみは 1、彫った模様は小さなダイスに見えることがあるので、駒の上のものは捨てる。
4. 同じダイスはしきい値を変えても何度も見つかる。場所ごとに読みを集め、4 回以上読めて 75% 以上が同じ目なら確か（`sure`）とする。
   偶然の模様は 1〜3 回しか読めない。
5. バーの上を除いて、確かなダイスがちょうど 2 つで、目の色（明暗）・大きさ・色が揃っているときだけ `values` を出す。
   1 つだけ（もう 1 つがカップの中など）、3 つ以上（2 人分のダイスが盤に出ている）は `null`。

## キューブの数字（`cube_value.py`、TODO-025、recognizer 0.21.0）

`cube.py` がキューブと決めた場所の、しきい値ごとに見つかった輪郭のそれぞれで数字を読み、多数決で決める。

1. 面を、輪郭の傾きに合わせて真っすぐな 80×80 の正方形に切り出す（`exact.warp`。辺の 90% を使う）。
2. 大津の二値化で、面の大部分と反対側の画素を「字」とする（白い面に黒い字も、黒い面に白い字も読む）。
   ほとんどが縁の帯（外側 10%）にあるかたまりは、面の縁の影や面取りなので捨てる。字が面の 3〜45% でなければ読まない。
3. 字を 4 通りの向き（90° ずつ）に回し、それぞれ外接の箱を 48×48 に収め、線を 1 画素の太さに細くして（Zhang–Suen）、
   ひな形の数字と「線どうしの平均の離れ具合」（市街地距離、両方向の大きい方）で比べる。点数は 1 −（平均の離れ）/ 8。
   太い字と細い字でも同じ数字なら合い、塗りつぶしのようなかたまりはどの数字にも合わない。
4. いちばん合う数字の点数が 0.74 以上で、ほかの数字より 0.10 以上高いときだけ、その輪郭はその数字と読む。
5. 2 つ以上の輪郭が同じ数字と読み、その票がほかのどの数字の 2 倍以上あるときだけ答える。それ以外は `null`（アプリは 2 とする）。

**ひな形は写真から学ばない。** OpenCV の Hershey フォント 6 種（普通・太字、正体・斜体）と、ふつうのフォント 19 種
（DejaVu、Liberation、Inter、Poppins、TeX Gyre など。`make_cube_glyphs.py` の `TEMPLATE_FONTS`）を、一度だけ `cube_glyphs.png` に描いてある。
本物のキューブの字体はこのどれでもないので、点数は余裕をもって決めた。計算はすべて整数か CPU で変わらない演算（CLAUDE.md の「精度の確認」）。

**確かめた写真。** サンプルで片側・盤の中にあるキューブは screen2 と tv-vegas-open（どちらも 2）だけで、4・8・16・32 を片側に置いた写真は無い
（PI-032 でネットも探した）。そこで、ユーザーの盤の写真 photo2・photo4 に、数字を描いたキューブを盤の面に沿って貼り込んだ
`samples/synth-cube-*`（12 枚、`synth_cube.py`）を作った。キューブの数字は、ひな形に使っていない別の 12 種のフォント
（`make_cube_glyphs.py` の `TEST_FONTS`。Bitstream Charter、Courier、GFS Baskerville、TeX Gyre Adventor など）で描き、向きはばらばら、
置き場所はトレイ・枠（手前・奥）と遊戯面の中、面は白・アイボリー・黒（白い字）など。アプリが送る大きさ（長辺 2048）に縮めてある。
貼り込んだ写真なので、ポイントの数は `check_accuracy.py` の合計に入れない（`"synthetic": true`）。

|---|---|---|
| screen2 | 奥の側に 2 | 2（当たり） |
| tv-vegas-open | 盤の中に 2（逆さま） | 2（当たり） |
| photo3、commons-diagram-holding | 真ん中に 64（横向き） | 64（当たり。真ん中なので解析には使わない） |
| screen1 | 真ん中に 64（筆記体） | 読まない |

| synth-cube-*（12 枚） | 2・4・8・16・32・64 を各 2 枚 | 9 枚当たり、1 枚読まない（GFS Baskerville の飾りの多い 32）、2 枚はキューブが見つからない（黒い面に白い字の 16 と、盤の中の 32） |

**間違った数字を答えたものはない。** 見つからない 2 枚は数字を読む前の `cube.py` の問題（黒い面は字が面の 4 割を超えて「数字らしい印」から外れる、など）。
本物のキューブの写真が手に入ったら `samples/` に入れて確かめる（`truth.json` の `cube` に `value` を書く。`evaluate.py` が「number ok / not read / WRONG」を出し、

## 面の列が 1 ポイント外へずれ、バーが広くなる（TODO-060、recognizer 0.21.3）

三角形の並びで四隅を合わせ直すとき（`geometry.fit_columns`）、左右の面ごとに 6 本の列を独立に合わせている。
バーの隣の三角形が駒の山で隠れていると、6 本を 1 ポイント外側（枠や駒の置き場の上）へずらしても、見える三角形は 5 本で同じだけ合う。
外側を選ぶと、隠れた三角形がバーに飲み込まれ、バーが 2 ポイント近い幅になり、そのあとの四隅もそれに引きずられる
（ユーザーの報告: 途中までうまく合っているのに、最後に中央のバーを無視して大きく読み違える。collected-l9azfe でバーの幅が 0.9 ポイント分 → 1.9 ポイント分）。

いまは面ごとに「何ポイントずらしたか」別に一番よい合わせ方を残し、2 つの面の内側の列の間が 2.5 ポイント（`MAX_GAP`。バー + 1 ポイント）より広いときだけ、
片方の面を 1 ポイント内側へ寄せた合わせ方を考える。寄せても点数が 0.6（`SHIFT_TIE`）以上は落ちず、
2 つの面の間が盤の真ん中の高さで面の色でない（バーらしい）割合が 0.1（`BAR_GAIN`）以上増えるときだけ寄せる。
バーが広い盤（commons-diagram-holding、内側の列の間が 3 ポイント）は、寄せると三角形が 1 本まるごと合わなくなるので変わらない。

## 撮影の傾きの警告

`recognize()` の `info` に `tilt_deg`（タップした四隅から推定した、真上からの傾き。0° が真上）と
`warnings`（40° を超えると `["oblique"]`）を入れている。サンプルでは真上から撮った写真が 12〜23°、
スクショが 0°、斜めの photo1（削除済み）が 69°。アプリはこれを見て撮り直しを勧める。

## 盤の位置（geometry）

`info["geometry"]` に、最後に合わせた盤の位置を入れている: 遊戯面の四隅（画像の画素）、12 列の中心と
バーの両端（遊戯面の幅に対する割合）。読み取り中の演出用に、見つけた三角形の先・駒の円・
ポイントごとに数えた駒の数と表示位置・ダイス（自信をもって読めた盤の中のもの）とキューブの四角（画像の画素）も入れている。
`recognize(..., progress=f)` とすると、段階が終わるたびに `f(段階, その段階の geometry)` を呼ぶ
（`fit`（四隅の合わせ直し 1 回ごと。枠の線で 2 回、三角形の並びで 2 回）→ `tips` → `checkers` → `counts` → `dice` → `cube`。
読み取りの結果は変わらない。API の `stream=true` が使う）。アプリは元の写真を盤面図にそろえて表示するのに使う。認識の結果は変わらない。

## 撮影ガイド（アプリで表示する想定）

- 盤の **真上から**、盤全体が画面いっぱいに入るように撮る。
- 影や照明の反射が強い所を避ける。

## 位置ごとに判定する読み方の試作（`slots.py`、TODO-032）

円を探す代わりに、射影変換の後に n 個目の駒が来る位置（根元から (n−0.5)×直径）ごとに「空き・暗い色・明るい色」を判定し、
「1 ポイントは 1 色で、根元から続けて積む」として各ポイントの (色, 数) を一度に決める。空いた位置と駒の見た目は、
円で読んだ結果から写真ごとに学ぶ（三角形の色と何番目かごとに、空いたと読んだ位置の色の中央値）。
`board.recognize(..., method="slots")`、`evaluate.py --slots` で動く。アプリは今までどおり円で読む。

2026-10-14、x86_64 で全 23 枚（552 ポイント）: **円 495、位置ごと 478**。

- 重みは総当たりで決めた（`SLOTS_TUNE=縁の重み,しきい値`）。円の縁の強さは空いた三角形の根元でも 0.4〜0.5 あり、
  重くするほど悪い（縁 1.0 で 403〜452、0.1 で 478、0 で 477）。色だけでほぼ決まる。

## 断面で数える読み方の試作（`section.py`、TODO-032 の案 2）

射影変換の後、各ポイントの中心線に沿って、幅 ±0.3 駒の帯の色の中央値を根元から並べる（断面）。各深さで
「駒の色」と「空いたときの見た目」のどちらに近いかを測り、根元から続く一番よい長さを山の長さとする（山に穴はない）。
数は 長さ ÷ 駒の直径（+0.2 で丸め）。山が盤の真ん中まで届くときは円の読みに任せる。縁の線のくり返し（自己相関）が
駒の直径より短ければその間隔で割る（アプリの画面のように重なった山）。
空いたときの見た目は、円の読みからではなく、**同じ色の三角形の列の断面の中央値**から学ぶ（多くの列は多くの深さで空いているので、円と一緒に外れない）。
駒の 2 色だけは円の読み（k-means）のものを使う。`board.recognize(..., method="section")`、`evaluate.py --section` で動く。アプリは今までどおり円で読む。

2026-10-15、全 24 枚（576 ポイント）: **円 525、断面 467**（帯の幅・しきい値・丸めを総当たりして 463〜468 の平らな所）。

- 盤面図・screen1・screen2・tv-vegas-open・photo3・dark-homeleft・nardy-midgame は円と同じ。
- 悪い: set-cube-dice 17 → 3、travel-case 16 → 7、leather-cups 12 → 5（木目や模様、盤の上の物で、空いたポイントを駒と読む）、
  tavli-burl 24 → 18（駒の色を取り違える）、photo4 23 → 18 など。数は 1 つ少なく読みがち（丸めの +0.2 はその補い）。
- 自己相関はこのサンプルでは結果を変えなかった（重なった山はほとんど真ん中まで届き、円の読みに任せる所に入る）。
- 円が出ない駒（dark-homeleft、TODO-027）は円と同じ 22 で、円の代わりにはならなかった。

**円と組み合わせると良くなる。** 断面だけが当たるポイントは 12（円だけが当たるのは 70）で、多くは円の「1 個だけの駒」の誤検出だった。
「円が 1 個だけと読み、断面が空と読んだポイントは空にする」と **525 → 530**（帯の幅などを変えても 527〜530、悪くなるサンプルはない。
dark-homeleft の 15、leather-cups の 9・21、rollup-oblique の 2・4・10、photo4 の 22）。
本番に入れる前に、TODO-051（円を放射対称で探す、0.20.0）の上で測り直すと **537 → 537** で効かなくなっていた
（断面だけが当たるポイントも 12 → 5。円の 1 個だけの誤検出の多くが、放射対称の円探しと TODO-048 で消えていた）。そのため本番には入れない（TODO-050、対応しない）。

## 半径を前提に円を探す（`radial.py`、TODO-032 の案 5、TODO-051 で本番に）

射影変換の後は駒の半径がほぼ決まっている（ポイントの幅の半分）。Hough は半径も探し、閉じたはっきりした輪郭が要るので、
代わりに放射対称変換（Fast Radial Symmetry Transform、Loy と Zelinsky 2003）で中心を探す: 勾配の強い画素（上位 30%）が、
勾配の向きに半径だけ離れた点に票を入れる（駒は周りより明るいことも暗いこともあるので両側に）。薄い縁でも、駒の縁の票は中心に集まる。
半径は 0.9・1.0・1.1 倍を試し、票の山（一番高い山の 25% 以上、半径の 1.3 倍以上離れたもの）を候補にする。
候補の採点（縁・色・`ring_same`）から先は今までと同じ。**recognizer 0.20.0（TODO-051）から、アプリもこれで探す。**
比べるために `board.recognize(..., method="hough")`（前の Hough）と `method="radial+hough"`（両方の候補）、`evaluate.py --hough` / `--radial+hough` を残している。

以下は試作（0.19.0、float で計算）のときの値:

2026-10-15、全 24 枚（576 ポイント）: **Hough 525、放射対称 536、両方 533〜535**。

| サンプル | Hough | 放射対称 |
|---|---|---|
| commons-rollup-oblique | 14 | 22 |
| commons-leather-cups | 12 | 15 |
| commons-dark-homeleft（円が出にくい焦げ茶の駒、TODO-027） | 22 | 24 |
| commons-travel-case | 16 | 18 |
| commons-case-dice・nardy-midgame・set-cube-dice・photo2 | 23・17・17・22 | 1 ずつ下がる |

- 放射対称だけのとき、山のしきい値は 0.25 で 536、0.3 で 534、0.35 で 529。票の厳しさ（ALPHA）と勾配の割合は両方の候補を使う形で振った:
  ALPHA 2 で 535（1 で 508、3 で 531）、勾配は上位 30% で 535（40% で 534、20% で 523）。
  `RADIAL_TUNE=ALPHA,勾配の百分位,山のしきい値` で変えられる。
- 円が出にくい駒（TODO-027）と斜めの写真（rollup-oblique）に効いた。Hough と候補を合わせると、Hough の誤った候補も残るので、放射対称だけより少し悪い。
- 遅い: このクラウドで 1 枚 5 秒 → 9 秒（`detect_checkers` を 4 回呼び、そのたびに 3 つの色の面で票を数える）。
- 試作の計算は float（Sobel・GaussianBlur・百分位）で、CPU によって最後の桁が変わりうるので、本番に入れる前に直した（下）。

### 本番に入れたときの直し（TODO-051、recognizer 0.20.0）

- **CPU で変わらない計算にした**（TODO-046）: Sobel は 16 ビット、強い勾配は百分位でなく順位（`np.partition`）で選ぶ、票は整数の数と和
  （向きの重みは `floor(√(gx²+gy²))`）、山の高さは `min(票の数, 10)² × 重みの和` の整数。浮動小数点は、IEEE 754 がどの CPU でも
  同じに丸める 1 演算ずつ（`sqrt`・割り算・掛け算・足し算と `rint`）でだけ使う。
- **ぼかしは箱フィルタ 3 回**（σ = 半径/4 の Gaussian の代わり、整数の累積和で、1 回ごとに窓の面積で割って桁を戻す）。
  2 回では 526、3 回で 537、4 回で 528。割らないと 3 回以上で int64 があふれ、488 などに落ちた。
- 半径は 3 段のまま（1 段では 496、2 段では 523）。
- **速さ:** `detect_checkers` は同じ画像で最大 4 回呼ばれるので、票の地図と山を画像と半径ごとに覚えて使い回す。
  このクラウドで 1 枚あたり、Hough 7.1 秒に対して 10.3 秒（試作は 11.8 秒）。Pi での時間は PI-035。
- 全 24 枚で **525 → 537**: rollup-oblique 14 → 22、leather-cups 12 → 15、dark-homeleft 22 → 24、travel-case 16 → 17、screen1 のキューブも見つかるようになった。
  case-dice 23 → 22（1 ポイントを −5 から −4 に、もう 1 つを外す）、nardy-midgame 17 → 16（もともと 1 個だけの駒を多く見落とす写真）が下がる。
- PWA と同じに縮めた実写真（`--app`）: photo2 24 → 21（5 個の山を 6 個と読む所が出る）、photo3 24 → 23、photo4 19 → 23。合計は同じ。
