### 5. `recognizer/corners.py:128` `_Upright` の `pad` が、古い傾きの上限 0.3 のまま

- コード: `self.pad = pad = int(0.3 * h) + 2`。`pad` と `SLOPES = arange(-60, 61, 2)` は同じコミット 7f95a3e で入っていて、0.3 は傾きの上限から来ている。

  | 写真 | k=-100 | k=-80 | k=80 | k=100 |

  | photo6 | 0 | 0 | 0 | 249 |
  | commons-rollup-oblique | 235 | 4 | 1190 | 4708 |
  | collected-bfqwve | 1051 | 325 | 852 | 1857 |
  | collected-4b88u3 | 339 | 0 | 0 | 0 |

- 捨てられるのは、写真の上か下の端から外へ出る線（切片が `-0.3h` より外）。`pad` を `_shift(h, max|SLOPES|) + 2` にしても、
  photo5・photo6・rollup-oblique・bfqwve・4b88u3 の結果は変わらなかった（実測）。実害は未確認。`SLOPES` を変えたときに一緒に変わらない値が残っている、という指摘

## 確かめて問題なかったもの

- `_shift` の整数計算: `t * k * 2` は 800 x 100 x 2 = 160000 で、int64 の範囲に十分収まる。`SLOPES[:, None]` との掛け算（corners.py:147）も同じ
- `_h_lines` の `pad = h`: `|k| = 100` で切片が `[-w/2, h + w/2)` を動くので、`w <= 2h` なら捨てる票は無い。横が縦の 2 倍を超える写真（またはそういう形に囲んだ `crop`）だけ、
  右端の急な線の票が落ちる。サンプルでいちばん横長の bfqwve は 800x427（1.87）で範囲内
- `_h_lines` の画素の条件 `gy > 2 * gx` は、縁の向きが水平から atan(0.5) = 26.6° までの画素だけを通す。新しい上限 0.5 とちょうど同じで、0.5 に近い線は票が半分ほどになる。
  食い違いではないが、0.5 を超えて広げても `_h_lines` では効かない
- `LINE_SEP` での間引き: `_h_lines` は x=0 での切片で、`_Upright` は帯の真ん中での位置で間引く（前からの作り）。調べた 6 枚の正解の奥と手前の辺は、x=0 で 163px 以上離れていて、
  間隔 12px で消し合うことはない
- `_meet` の分母 `1 - kh * kv / 40000` は 0.75 より小さくならない（0.23.1 では 0.91）
- 版: recognizer だけ 0.23.1 → 0.23.2（直し）。analyzer は変えていないので `APP_VERSION` も触らないのが決まりどおり
- README に足した文に TODO の番号も archives のパスも入っていない。corners.py のコメントは「なぜ 0.5 か」（photo5 0.36、photo6 0.39）を書いている
