## きっかけ

docs/PI_CHECKS.md の「スマホ:」の確認がユーザー待ちで溜まっていた（PI-013〜015、PI-017）。
ユーザーの問い「どれか自動化できないかな？」に、Pi の上で Playwright から PWA を操作すれば大半を代われると答え、そのまま着手した。

## やったこと

- `tools/pi_ui_check.py`: Pi の上で `http://127.0.0.1:8000/` の PWA を、スマホと同じ画面の大きさのヘッドレスの chromium で操作する。
  Playwright は `uv run --no-project --with playwright` で入れ、ブラウザは Pi の `/usr/bin/chromium` を使う（Playwright 1.64.0 の
  ブラウザは入っていなかったので、ダウンロードせずに済ませた）。どれも `samples/screen1.png` を読み取ってから確かめる。
  - `double`: キューブを片側・「ダブルされたところ」にしたまま読み取り、最善手とキューブの説明を見る
  - `speech`: `speechSynthesis.speak` を差し替えて、読み上げる文に勝率・ピップ・% が無いかを見る
  - `export`: 共有の画面を消して（PC の動き）、ダウンロードされる 2 つのファイルと中身を見る
  - `collect`: 「解析の設定」の下のスイッチを押し、オフでは `collected/` が増えず、オンで 1 組でき evaluate.py で測れるかを見る。作った組はコンテナの中で消す
- docs/PI_CHECKS.md の「Pi の上の Claude Code がやること」に、スマホの画面の操作はまずこれで確かめる手順と、確認の一覧を足した。CLAUDE.md のコマンドに 1 行足した
- PI-015 と PI-017 をこれで決着させた。PI-013 と PI-014 は、実際の音声と iPhone の共有の画面・添付だけを「スマホ:」に残した

## 確かめたこと

- verifier: 文書のコマンドどおりに 4 つとも OK・終了コード 0、`collected/` は前後で差なし。アプリの `app.js` を壊したコピーを 8001 番で動かすと、
  (a) 読み上げに勝率を入れる → `speech`、(b) キューブの説明を変える → `double`、(c) truth.json を作らない → `export` が、それぞれだけ FAIL になった

## 残ること

- `collect` は evaluate.py が終了コード 0 で測れることだけを見て、点数は判定に入れていない（verifier の指摘）。PI-015 の期待が「測れる」なので、このままにした。
  点数は認識の精度の話で、`recognizer/evaluate.py` と README の「精度」の表で見る
- 読み取りの前にキューブを置く操作は、画面ではなく `setCube` を呼んで再現している（読み取り直しのときの状態と同じ）

## 分担の振り返り

- verifier は、アプリを壊したときに狙った確認だけが落ちることを実測で示し、`collect` が点数を見ていないことを見つけた。
  main が自分で流したときは全部 OK になるのを見ただけで、判定の強さは確かめていなかった
- 見込みどおりの編成で動いた。reviewer はアプリのコードを変えないので入れなかった
- 次に確認のスクリプトを足すときも同じ編成でよい。壊したアプリを別のポートで動かすやり方は、依頼文にそのまま書けば使い回せる
