## きっかけ

ユーザーが、`tools/live_view.py` の窓で画面の下端がはみ出ていると言った（2026-10-17）。開発機の画面は 1920×1080 で、表示領域 412×915 の窓が収まらなかった。
直し方を聞くと、ユーザーは「Pixel 9a を想定したサイズにしてみて」と答えた。

## やったこと

- Playwright の端末一覧に Pixel 9a は無いので、画面 1080×2424・密度 2.625（CSS で 412×923）から、同じ作りの Pixel 8a（Playwright で 412×839、全体 914）と同じ割合で、
  Chrome の表示領域を 412×848 とした。`tools/live_view.py` の `PHONE` と `DENSITY`（2.625）、`docs/raspi.md` の書き方
- 窓の大きさを `--window-size` で決めようとしたが効かなかった。窓（978×1012）はウィンドウマネージャーが決めていて、表示領域とは別。指定は外した

## 確かめたこと

- live_view を起動し直し、表示領域が 412×848、密度 2.625 になったことを CDP で読んだ
- ユーザーが、窓の下端が収まっていることを目で確かめた
- PR #326 の GitHub Actions の `test` が通った

## やらないと決めたこと

- live_view で読み上げを鳴らすこと。開発機には speech-dispatcher が無く、Chromium も Google Chrome（dev）も日本語の声が 0 だった。スマホと同じ声（Android の Google の声）は Linux では使えない。
  Google 翻訳の読み上げ（`translate_tts`）は音声を返したが（公式でない API で、文を Google に送る）、ユーザーが項目にしないと決めた。声はスマホで確かめ、live_view では文だけを確かめる

## 分担の振り返り

- 確認の担当を立てなかった。道具の定数を変えるだけで、窓が収まるかはユーザーの画面でしか確かめられなかったため。ただし `~/.claude/CLAUDE.md` はコードを変える項目には確認の担当を分けるとしているので、
  次に同じ規模の項目でも、窓の大きさを読み出す確認は verifier に任せ、目で見る分だけユーザーに頼む
