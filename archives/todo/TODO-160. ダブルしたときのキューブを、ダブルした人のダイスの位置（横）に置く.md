## きっかけ

TODO-156・TODO-158 で、ダブルされたところのキューブを、ダブルされた人の側のダイスの位置（横）に描くようにした。手前がダブルすると左の場に出る。ダブルした人のダイスの位置に描くほうが分かりやすいので、横の位置を変えることにした（2026-10-20 ユーザーが決めた）。

## やったこと

PR #475、analyzer 0.89.1。

- `analyzer/static/board-view.js` の `drawCube` で、ダブルされたところのキューブの横を、ダブルした人のダイスの場にした。縦は今のまま、ダブルされた人の側の半分（真ん中から ±75.25）。手前がダブルすると右の場の奥寄り、奥がダブルすると左の場の手前寄りに出る
- 最初の版を画面で確かめると、`collected-galaxy-screen-1` で手前がダブルしたとき、キューブが 21 のポイントの 3 つ目のチェッカーに重なった。そこで、横の位置を局面ごとに選ぶようにした（ユーザーが決めた）。`offeredCubeCentre(b, home, at)` で、場の真ん中を先に見て、チェッカーの円（縁を含む）と重なるときだけ、真ん中に近い順に 6 つのポイントの上を見る。同じ距離なら、どちらの場でもバー寄りを先に見る。どこも重なるときは場の真ん中
- 候補は、最初は 24 ずつ離れたポイントの上とポイントの間にしたが、reviewer が、ポイントの間は選ばれることが無いと指摘したので、ポイントの上だけにした
- `analyzer/README.md` の説明と `board-view.js` のコメントを直し、`test_pwa.py` に `test_offered_cube_keeps_clear_of_checkers` を足した。`board-view.js` に `module.exports` を足した（テストから呼ぶため）

## 確かめたこと

- `uv run pytest analyzer/test_pwa.py` 34 passed。`test_offered_cube_keeps_clear_of_checkers` は、空の盤で真ん中（手前・奥）、重なる局面で 24 ずれる（手前・奥）、重ならない局面で真ん中、全部のポイントに 5 個で真ん中、21・22 の両方に 3 段あるときバー寄り（右の場で左、左の場で右）を見る。判定を常に真・常に偽にする、バー寄りの向きを固定する、±3 の順を逆にする、のどれでも落ちることを確かめた。判定のすきまの閾値を少し緩めても落ちないが、起こりうる距離は「約 3.7 以下」か「26.75 以上」しかなく、その間のどこでも結果は同じ（reviewer が実測）
- reviewer は、横・縦・チェッカーの y・閾値・バーとの間・矢印との間が式として合っていることを確かめ、候補の順（バー寄りを先にする向きの揃え）、ポイントの間の候補が要らないこと、README の書き順を指摘した
- verifier が live_view のブラウザで確かめた。最初の版では手前のダブルがチェッカーに重なった（すきま −17.5）。直したあと、手前のダブルは右の場の奥寄り（場の中心から 24 右へずれ、チェッカーとのすきま 5.6）、奥のダブルは左の場の手前寄り（すきま 72.2）。矢印との間は 6.0、ダイスは 0 個。app-grey-shot（home=left）でも、ずれずに場の真ん中に出た
- GitHub Actions の `test` が通ってマージした
- ローカル: マージ後にローカルホストで、`/version` が analyzer 0.89.1（コミット dec451f）。`collected-galaxy-screen-1` を認識して、手前がダブル（`{black, 2, offered: true}`）にすると、キューブの中心は SVG の (516, 144.75)（右の場の奥寄り。場の真ん中 492 から 24 右にずれた）、チェッカーとのすきま 5.62。奥がダブル（`{white, 2, offered: true}`）にすると (164, 295.25)（左の場の手前寄り）、すきま 72.23。ダイスは 0 個

## 分担の振り返り

- **見つけたこと:** verifier は、最初の版で、手前のダブルがチェッカーに重なることを画像と数値で見つけた（直したあとの再確認で、重ならないことも確かめた）。reviewer は、バー寄りを先に見る向きが左右で揃っていないこと、選ばれることの無い候補（ポイントの間）、README の説明の順を見つけた。implementer は、自分でテストを足し、判定を壊すと落ちることを確かめたが、順の違いは見つけられなかった
- **見込みと食い違った理由:** 見込みは「位置の式だけで分岐は変わらないのでレビューは要らない」だった。確認で重なりが見つかり、重なりを避けて選ぶ分岐が入ったので、見込みを書き直さず、reviewer を足した（実施の行）。重なりは、チェッカーの多い 1 サンプルでしか確かめていなかった最初の見立てが原因
- **次に同じ規模なら:** 描く位置を変える項目では、最初から、チェッカーが多い局面（積み上げが 3 段以上）を確認に含める。位置の選び方に分岐が入るなら、見込みの時点で reviewer を入れる。順序のあるリストから選ぶ実装は、順を逆にすると落ちるテストを、最初から求める（今回は reviewer の指摘で足した）
