## やったこと

recognizer 0.11.0（`recognizer/board.py`、PR #112）。

- 焦げ茶の駒の色（L48 a140 b139）は赤い三角形の底（L42 a150 b142）とほぼ同じで、縁の強さも空いた所（三角形の白い縁取り）と重なり、どちらでも分けられないことを測った
- 代わりの手がかり: 列の中央付近の空いた位置には三角形の辺（縦に近い線）が見え、駒があると隠れる。
  駒 1 個ずつの位置で横向き÷縦向きの勾配の比を測ると、dark-homeleft では駒のある所 0.5〜1.5、空いた所 5〜10 に分かれた。
  全サンプルで「辺が見える」の判定は 1,057 か所中 17 か所、「隠れている」は 270 か所中 27 か所が正解と食い違う（ダイス・カップなど）
- `column_texture`: 位置ごとの比を同じ列の 12 列の中央値と比べ、0.7 倍より大きければ "shown"、0.35 倍より小さければ "hidden"（中央値 3 以上の深さだけ）
- `detect_checkers`: "shown" の位置の円を捨てる。ただし同じ列に捨てない円が 2 個以上あり、それと縦に続く円は残す（強い斜めの写真で山の根元を捨てていた）
- `add_hidden_stacks`: 深さ 1 から続けて "hidden" の列（円が 1 個以下）に駒を足す。数える直前の 1 回だけ（駒の大きさや盤の色の学び直しに入れると ai1 の盤の写真が下がった）
- 駒の大きさの測り直しは、捨てる前の円で行う（下の x86_64 の件）
- `accuracy_baseline.json` を CI（x86_64）の値で書き直し、`recognizer/README.md` の説明と精度、`docs/PI_CHECKS.md` の PI-022 を足した
- しきい値は環境変数で総当たりして決め、試験用の分岐は消した（円が 0 個の列だけ足す 503、1 個以下 504、列のずれの許容 0.4 は photo3 が −1、など）

## 確かめたこと

- 全 23 枚: x86_64 は 495 → 506、Raspberry Pi は 492 → 503。dark-homeleft 12 → 20、set-cube-dice 12 → 15。ほかはポイント・バー・ホーム・ダイス・キューブとも変わらない（verifier、CI の accuracy）
- ai1 の盤の写真（Pi の `collected/` の 5 組）: 23・19・15・18・22 → 24・19・14・18・22（合計 97 で同じ。下がった 1 組は直す前から列がずれた斜めの写真）
- 同じ円が重なって出ても落ちない、`TEX_SHOWN`・`TEX_HIDDEN` を外すと dark-homeleft が 12 に戻る（verifier）
- x86_64 でだけ set-cube-dice のキューブが見つからなくなった。CI に一時的な調査を足して測ると、捨てたあとの円で駒の直径が 89.7 → 91.8 に変わり、
  探すキューブの大きさがずれていた。捨てる前の円で測るように直して解消（そのかわり dark-homeleft は 22 → 20）

## 分担の振り返り

- reviewer は、同じ円が 2 つあると `in` の比較で `ValueError` になること（Hough の 3 チャンネルの重複で実際に起きうる）、深さ 4 が反対の列に入りうること、
  足した駒がダイス・キューブの読み取りに効きうることを見つけた。最後の点は x86_64 の CI で実際に起きた（原因は足した駒ではなく、捨てた円による駒の大きさの変化）
- verifier は期待どおりの値を 2 回とも再現し、`collected/` が 4 組から 5 組に増えていたことを見つけた。食い違いは見つけていない
- 見込みとの食い違い: 担当の組み方は見込みどおり。reviewer の 1 回目を上限で捨てたのと、x86_64 でしか起きない件で main の調査（CI を 3 回回した）が増えた
- 次に recognizer を変える項目では、Pi で測り終えたら reviewer の前に一度 PR を出し、CI の accuracy（x86_64）の結果を先に見る。
  x86_64 でしか起きない差は Pi の verifier では捕まえられず、今回はそれでレビュー後の直しと再測定が 1 巡増えた
