# 局面解析 API（ステップ2）

盤面（gnubg Position ID、または認識結果の `points`）を GNU Backgammon で解析し、
勝率・ギャモン率・バックギャモン率・エクイティ・ピップ数と、どちらが有利かを返す HTTP API です。
PWA（下記）から呼び出します。

GNU Backgammon 本体は PyPI の [`gnubg`](https://pypi.org/project/gnubg/) パッケージ（gnubg のニューラルネットと
ベアオフDBを同梱した Python バインディング）を使います。apt で gnubg を入れる必要はありません。

## 起動

```
uv sync
uv run uvicorn app:app --app-dir analyzer --host 0.0.0.0 --port 8000
```

`--reload` や複数ワーカーは使わないでください。gnubg の拡張モジュールはメインスレッド以外で
1手読み以上の評価をするとクラッシュするため、解析は専用の子プロセス（そのメインスレッド）で行っています。

## PWA（ステップ3）

起動したサーバーの `/` をスマホのブラウザで開くと使えます（`analyzer/static/`、ビルド不要の HTML / JS）。

**作り（0.39.0）:** 画面に出るものはすべて `app.js` の `state` にあり、変えるのは `update(patch)` だけ。
`update` のあとに `render()` が、画面の部分ごとに、出す内容が前と変わった所だけを描き直す（`part(key, draw)`）。
ボタンなどの操作と、サーバーとのやりとり（写真の読み取り・解析）は `update` を呼ぶだけで、画面には直接触らない。
最近の写真（`history.js`）への保存も `state` から自動で行う。描く・計算するファイルは `state` を知らず、渡されたものだけを使う:
`board.js`（盤面のデータと操作）、`board-view.js`（盤面図の SVG）、`corners-view.js`（四隅を合わせる写真）、
`result.js`（結果の表と読み上げの文）、`api.js`（サーバー）、`cube.js`・`moves.js`・`photo.js`・`scan.js`・`sample.js`。
外から確かめるとき（`tools/pi_ui_check.py`）は `window.BgApp`（`state`・`update`・`rolled`）を使う。

**画面を変えずに作りを変えたとき**は、`tools/ui_snapshot.py` で前の版と比べる。クリックだけで 3 つの流れ（手入力・写真・最近の写真）を操作し、
各段階で**見えている**画面（部品の表示、文字、盤面図の SVG、写真の画素のハッシュ、結果、読み上げの文）を記録する。
`record before.json`（前の版のサーバーに向けて）、`record after.json`、`compare before.json after.json` の順で、違いがあれば場所を出して終了コード 1。
2 つの版を並べて動かす手順はファイルの先頭に書いてある。0.39.0 の作り直しは、これで前の版と 52 か所すべて同じことを確かめた。

**画面の並び（TODO-086）:** その画面の主な操作（「盤面を読み取る」「解析する」「読み上げ」と、前に読み取った盤面を開くボタン）は、
ヘッダーではなく画面の下に固定したバーにある（写真の選択の画面では出さない）。押せるものは高さ 44px 以上。
プレイヤーは画面・結果・読み上げで駒の色で「白」「黒」と呼ぶ（手前の駒の色で「明るい方」を選ぶと手前が白、「暗い方」なら手前が黒）。
写真の向きそのものを言う所（四隅の画面の「手前のホーム」「手前の駒の色」など）は「手前」のまま。

1. 「写真を撮る」でカメラを開くか、「写真を選ぶ」で端末の写真を選ぶ（アプリ画面のスクリーンショットも可）。「手で入力」で写真なしに初期配置から手入力もできる。3 つのボタンの下の「うまく読み取るコツ」（閉じてある）を開くと撮り方のコツが出る。
2. 盤の遊戯面の四隅に初期値の点が出る（`/find-corners` で推定。見つからないときは画像の内側の長方形）。
   ずれていればドラッグで合わせる（指の下はルーペで拡大表示）。「四隅をやり直す」で 左上→右上→右下→左下 の順にタップし直すこともできる。
   その下に「画像を編集」「もう一度検出」「Claude に選ばせる」と、盤面の画面と同じ「ゲーム」（マッチの長さとスコア。どちらの画面で直しても同じ値）がある。
   「画像を編集」（TODO-070）で写真そのものを回し（「左に 90°」「右に 90°」と ±45° のスライダー）、写真の上を斜めにドラッグして盤のまわりを囲む。
   「確定」すると、回して切り抜いた画像（端末の canvas で作る）がそれ以降の写真になり（読み取りに送る画像・最近の写真・サーバーに保存するものも）、その画像で四隅を探し直す。
   読み取った盤面や設定はそのまま残る。切り抜いた画像は、盤が画像の大部分を占めてよいものとして探す（`/find-corners` に画像全体を `crop` で送る）。
   「もう一度検出」は、ユーザーが動かした・タップした隅をそのままにして、残りの隅を探し直す（見つからなければ四隅はそのまま）。
   「Claude に選ばせる」（TODO-082。`claude` が使えるサーバーだけに出る）は、写真を Anthropic に送って Claude に四隅を選ばせ、4 つとも置き換える。
   待つ間の「取り消す」でやめられる。失敗したときは四隅はそのまま。
   「四隅を固定する」（TODO-084）にチェックを入れると、読み取りで四隅を枠や三角形に合わせ直さない（`keep_corners`）。
   点を手で動かすとチェックが入り、新しい写真・画像の編集・「もう一度検出」で見つかったとき・Claude の四隅では外れる。
   「横から撮った」（TODO-120）にチェックを入れると、盤の真横（対局者の位置から 90° 回った位置）から撮った写真として四隅を探し直し、
   読み取りもそのやり方にする（`/find-corners` と `/analyze-photo` に `side` を送る）。初めて入れたときだけ「撮った位置」（手前の人から見て右から／左から）を聞く。
   選んだ位置とチェックは端末に覚え、次の新しい写真もそのまま始める。写真ごとにも「最近の写真」に残し、開き直したときは端末の設定より写真に残したものを使う。
   位置はチェックが入っている間、いつでも選び直せる。チェックや位置を変えると四隅を探し直す。手で動かした隅は写真の上の場所のまま残し
   （新しい向きでの名前に付け直す。右から撮った写真では写真の右上が左上）、残りの隅だけを探す。手で動かした隅が無ければ 4 つとも探し直す。
   「Claude に選ばせる」の四隅（写真の下を手前とした順）も、横からのときはその向きの名前に付け直して使う。
   モードと左右は写真ごとに履歴にも残し、開き直したときはそれで読む（端末に覚えた既定より優先。0.68.0 より前に残した写真は普通のモード）。
   手前の人のホーム側（自動/左/右。自動なら駒の並びから推測）と駒の色（暗い方/明るい方）を選んで画面の下の「盤面を読み取る」。
3. 読み取った盤面が出るので、違うポイントやバーを盤の上で直す（TODO-059）。
   盤の番号は手番の人から見た番号（自分のホームの端が 1。奥の人の番なら、手前の人から見た n が 25−n になる。TODO-089）。最善手の棋譜の番号と揃う。
   - タップ: 根元から何段目かで、その段まで駒を置く（3 段目なら 3 個）。一番上の駒をタップすると 1 個減る。
     駒が 5 個以上ある所は 5 段目のタップで 1 個ずつ増える。空の所には「空の所に置く色」の色で置く（最後に置いた色に切り替わる）。
     盤の縁のポイントの番号をタップすると空になる。バーは上半分が手前、下半分が奥の駒（どちらも真ん中から外へ積む）
   - 長押し（パソコンは右クリック）: 指のそばに吹き出しが出て、白／黒と 0〜15 の数を選ぶ。色を間違えた所や数が大きくずれた所に使う
   - 「元に戻す」で手で直した分を 1 つずつ戻せる（写真を読み直したり、色を入れ替えたり、ホームの左右を選び直したりすると戻せなくなる）
   - 駒の数が合わないときだけ、盤のすぐ下に「⚠ 白 14/15」のような短い印が出る（盤上とバーの数 / 15。TODO-088）。
     15 個より多いとき、写真から読んだ盤で 15 個より少ないとき（上がったか見落としたか）、盤に駒が無いときに出る。
     15 個より多いときと盤に駒が無いときは解析できない
   手前の人のホームの左／右の切り替え（画面では「白のホーム」か「黒のホーム」。選び直すと盤を鏡写しにする）がある。
   設定の下に「色を入れ替え」「初期配置」のボタン、その下に「読み取りの改善」（写真から読んだときだけ。「サーバーに［保存する］［保存しない］」と「ファイルに書き出す」）。
   ホーム側を自動にして、駒の並びから左右を決められなかったときだけ、切り替えの下にそう出す（逆なら選び直す）。
   盤の上に転がっている 2 つのダイスが写真から読めたときは、ダイスの目に初期値として入る（値の横に小さく「写真」と出る。直すと消える）。
   読めないとき・自信がないとき（1 つしかない、3 つ以上ある、バーやカップの中など）は空のまま。
   次に振る人とダイスの目（任意。ダイスを入れると、画面の「次に振る人」は「振った人」に変わる。結果の文と読み上げも同じ）、読みの深さ（2手 / 3手。「解析の設定」の最後。選んだほうを端末に覚える）を選んで画面の下の「解析する」。どちらかの駒が16個以上のとき、盤に駒が無いとき、クロフォードのゲームでキューブが中央でないときは、「解析する」をグレーアウトし、その上に理由を出す（直すとすぐ押せるようになる。TODO-116）。上がった駒は盤面図の上下の行のトレイに出る（手前は盤の下、奥は盤の上）。それぞれのピップ数も、トレイの横にその人の駒の色の札で「PIP 167」のように出る（盤面を直すたびに数え直す）。ダイスの目が入っているときは、盤面図にもダイスの絵が出る
   （次に振る人の右手側のフィールド、つまり手前なら右・奥なら左に、その人の駒の色で）。盤面図の真ん中には、次に振る人の駒が進む向きを U 字形の矢印で出す（その人の駒の色で半透明に）。
   **キューブ**は場所（中央 / 白 / 黒）と数を選ぶ（`static/cube.js`。盤面図では持っている人の側の行（手前は盤の下、奥は盤の上）の、トレイと反対側の端に出る。誰も持っていないときは盤の下の行のバーの真下）。写真から場所が読めたときは初期値に入る（遊戯面の中にあれば、次に振る人がダブルしたところとして相手の側に置き、ダイスを消す）
   （値の横に小さく「写真」と出る。数は写真の数字を読む。読めなければ 2。違えば直す）。ダイスがなければ、中央なら次に振る人がダブルすべきかを、
   片側にあれば「その側がダブルされたところ」としてテイクかパスかを判定する（次に振る人はダブルした側に自動で変わる）。
   ダイスがあれば、キューブが中央か次に振る人の側にあるとき、振る前にダブルすべきだった場合だけそう出す（TODO-096）。
   「ダブルされたところ」にチェックが入っている間はダイスの目の欄を出さず、入れてあったダイスも解析に使わない（TODO-086）。写真からダイスが読めたときは、チェックを外す。
   「ダブルされたところ」を外すと、その側がキューブを持っている扱いになる（持ち主が次に振るならリダブルすべきかを判定）。
   **マッチとスコア**（TODO-066）は盤面の画面の「解析の設定」の先頭の「ゲーム」で選ぶ（TODO-086。結果の画面では変えられない）: 「アンリミテッド」か「N ポイントマッチ」（1〜25）、白と黒のスコア、
   片方だけが残り 1 ポイントのときは「クロフォード」（このゲームはダブルできない。キューブを片側に置いているあいだは「解析する」を押せない）。
   選んだ値は端末に覚え、次に開いたときもそのまま。写真からの読み取りにも使う。
   マッチのときは、盤面図の上に「7 ポイントマッチ（クロフォード）」の行が足され、それぞれのスコアがその人の行のホームと反対の端（キューブの内側）に「3 点」のように出る（TODO-099）。
   「解析の設定」は ゲーム → キューブ（数とダブルされたところ）→ 次に振る人 → ダイスの目 の順に並ぶ（TODO-088）。
4. 解析すると**結果の画面**に移る。上に盤面図（ここでは直せない）、下に概要の文、勝率の棒グラフ、キューブの判断（ダイスを入れたときは、振る前にダブルすべきだった場合だけ「キューブ（振る前）」として。gnubg がダブルまでの遠さを出したときは「ダブルまでの遠さ 26%・ダブルにはまだ少し早い」のように、四捨五入した数字で 10% 未満「一歩手前」、30% 未満「まだ少し早い」、それ以上「まだ遠い」と添える）、ダイスを入れたときは最善手5つ（見出しの下に「Luck +0.329・良い目」のように、そのロールの Luck を数字と言葉で。区切りは gnubg と同じく ±0.3・±0.6 を超えたら）、勝率・ギャモン率・エクイティ・ピップ数の表の順に並ぶ（TODO-090）。
   直すときはヘッダーの戻る（スマホの戻るでも）で盤面の画面に戻る。盤面も設定も変えずにもう一度「解析する」を押すと、解析し直さずに同じ結果を出す。
   最善手は盤面図に矢印で出る（最初は 1 位の手。一覧の行をタップするとその手の矢印に変わる。矢印はダイス 1 つにつき 1 本で、「22/15」なら 22→17 と 17→15 の 2 本。途中や行き先でヒットした所は赤い丸。手の表記の読み方は `static/moves.js`）。盤面を直すと矢印は消える。矢印は結果の画面の盤面図だけに出て、盤面を直す画面の盤面図には出さない。
   写真から読み取ったときは、元の写真も出して読み間違いを見比べられる（下記）。
   画面の下の「読み上げ」ボタン（スピーカーの絵と文字。解析したあとに出る。読んでいる間は「■ 止める」で止める）で、最初に、振る前にダブルすべきだったときはそのこと（TODO-096）、次にダイスを入れたときはそのロールが良い目か悪い目か（ふつうの目なら言わない。TODO-100）と最善手を、ないときは次が誰の番かを言い（キューブの判断を読むときは、その文に誰のことかが入るので言わない）、続けてキューブの判断と形勢（「かなり有利」「ほぼ互角」など）を日本語で手短に読み上げる。ダブルしてもしなくてもよいときは、キューブの判断は読まない。終局しているときは、どちらの勝ちで終わっているかだけを読む。読み上げでは「白の人」でなく「白」と言う。マッチのスコアは読まない（盤面図に出ている。TODO-099）。勝率やピップ数の細かい数字は読まず、画面にだけ出す（ギャモンの見込みが大きいときとレースの差が 20 ピップ以上のときは一言添える）。結果の表と読み上げの文は `static/result.js` が作る。
   盤面の画面の「解析する」の上の「解析後、自動で読み上げる」をオンにすると（既定はオフ。選んだほうを端末に覚える）、解析して結果の画面に移ったときに同じように読み上げる。スマホのブラウザは押した直後でないと音を鳴らさないので、「解析する」を押したときに無音を鳴らして、あとから鳴らせるようにしておく（TODO-115）。
   声は、サーバーが 1 文ずつ Google 翻訳の読み上げに頼んで作る（`GET /speech`。どの端末でも同じ声になる。読み上げの文が Google に送られる）。Google 翻訳の読み上げは公式の API ではなく、止まったり断られたりすることがあるので、そのときは残りの文をブラウザ標準の音声合成（Web Speech API。声は端末しだい）で読む。

**元の写真の表示（`static/photo.js`）:** 四隅で台形補正した写真を、盤面図と同じ向き・同じポイントの並びで出す。
「元の写真を並べる」のチェックを入れると盤面図の横に並べ（広い画面では左右、スマホでは上下）、外すと隠す。
写真は見るだけで、タップしても何も起きない（TODO-088）。補正には `/analyze-photo` が返す `geometry`
（認識が見つけた盤の四隅と列の位置）を使い、写真の列を盤面図の列にそろえる。補正は端末の中で行い、写真を追加で送ったり保存したりはしない。

**四隅探しと読み取りの途中経過（`static/scan.js`）:** サーバーは段階が終わるたびにその結果を送り（`stream=true`）、
アプリはそれを順に並べて **1 段階ずつ** 写真の上に見せる。どちらも最後の段階を見せ終えたところで完了とする（タップで飛ばせる）。
- **四隅探し**（写真を読み込んだ直後、`/find-corners`）: 写真全体に走査線 → 横の縁の候補の直線（橙）→ 縦の縁の候補の直線（青）→
  盤らしい四角形の候補（黄。いちばん盤らしいものを最後に濃く）→ 四隅（緑）。
  見せ終えたら四隅の点を置く（見つからなければ長方形）。写真をタップすると表示をやめ、すぐ四隅を動かせる
  「もう一度検出」と画像を編集したあとも同じ表示
- **読み取り**（「盤面を読み取る」）: 四隅から描いた盤の枠・三角形・バーを遠近どおりに重ねて走査線 → 四隅の合わせ直し 4 回
  （枠の線で 2 回、三角形の並びで 2 回。枠が少しずつ寄る。「四隅を固定する」では列だけ合わせる 1 回）→ 三角形の先 → 駒の円 → ポイントごとの数（とホームの向き）→
  ダイス（四角と目）→ キューブ（四角）。最後のあと、解析がまだならその絵のまま待つ

**写真の上に出す文字は数字だけ**（ポイントごとの数とダイスの目。段階の説明や「見つかりません」などの文字は出さない。ユーザー、2026-10-15）。

**各段階を見せる長さは `scan.js` の `STAGE_MS` の表で、段階ごとに変えられる**（2026-10-16 の時点では、どの段階も 500 ミリ秒。TODO-061）。
段階を一度に受け取ったとき（流さない古いサーバー、途中でまとめてしまう経路）も、同じ順に表の長さずつ見せる。
端末が「視差効果を減らす」（prefers-reduced-motion）なら動かさず、各段階を止まった絵で見せる。
写真の上に描くだけで、読み取りの結果は変えない。

- 読み込んだ写真は、最近の 100 枚まで「最近の写真」に残る（`static/history.js`）。写真を選んだ時点で入り、
  選ぶと盤面を読み取る前の四隅の画面から、指定した四隅・ホーム側・駒の色のまま始まる。読み取って直した盤面も残っていて、
  「前に読み取った盤面を開く」で開ける。残すのは**使っている端末の中（IndexedDB）だけ**で、サーバーには残らない。
  写真は長辺 2048px に縮めて（小さいスクリーンショットはそのまま）保存し、古いものから自動で消える。✕ で 1 枚ずつ消せる。
- 盤面の画面の「ファイルに書き出す」（`static/sample.js`）は、写真と、手で直した後の盤面を
  `user-日時.jpg` と `user-日時.truth.json`（`samples/*.truth.json` と同じ形）の 2 つのファイルにする。
  共有の画面で送れる端末（iPhone など）では共有の画面が開き、送れない端末（JSON を共有できない Android の Chrome や PC）では 2 つともダウンロードになる。サーバーには何も送らない。
  JSON には認識が読んだ盤面（`read`）と、直したポイントの番号（`fixed_points`）も入る。使い方は TODO-030。
  横から撮った写真として読んだときは `side`（`right` か `left`）も入る（`evaluate.py`・`check_accuracy.py`・`collected.py` はそのモードで読む。TODO-120）。サーバーに保存する組（`POST /samples`）も同じ。
- 長辺 2560px を超える写真は、ブラウザで長辺 2048px に縮めてから送る（この大きさでのサンプルの精度は [recognizer/README.md](../recognizer/README.md) の「精度」の「アプリ経由」の列）。
- 別のホストに PWA を置くときは `?api=https://APIのURL` を付けて開く。
- ホーム画面への追加と Service Worker は HTTPS（または localhost）のときだけ有効。
- **Android** でホーム画面に追加すると、写真アプリなどの「共有」の一覧に BG Analyzer が出る（manifest の `share_target`）。
  共有した写真は Service Worker が端末の中で受け取り（`sw.js`）、選んだときと同じく四隅の指定に進む。サーバーに送るのは「盤面を読み取る」のときだけ。
  Service Worker がまだ動いていないとき（追加した直後など）は、サーバーの `POST /share-target` が写真を読まずにアプリへ戻し、選び直すよう表示する。
  iPhone（Safari）には PWA を共有先にする仕組みがないので、アプリ内で選ぶ。

## Raspberry Pi で常駐させる

arm64 の gnubg は PyPI に wheel がないので、このリポジトリの Release に置いた wheel を使う（`.github/workflows/gnubg-wheel.yml`）。
自宅の Raspberry Pi で公開する手順は [docs/raspi.md](../docs/raspi.md)（systemd の `bganalyzer.service` と Tailscale Funnel）。PWA は API を相対パスで呼ぶので、`/bg/` のようなパスの下に置いても動く。

## API

色の呼び方は認識側と同じです: **white = 写真の手前のプレイヤー、black = 奥のプレイヤー**。

### `POST /analyze`（JSON）

| フィールド | 説明 |
|---|---|
| `position_id` | gnubg Position ID（`board` とどちらか一方） |
| `board` | `{"points": [24個], "bar_white", "bar_black", "off_white", "off_black"}`。`points[i]` は手前側から見たポイント i+1、正 = white、負 = black。off は省略すると 15 − 残りで補完 |
| `on_roll` | 次にサイコロを振る側 `"white"`（既定）/`"black"` |
| `plies` | 読みの深さ 0〜3（既定 2。2 で 1局面 約30ms、3 で 約0.7秒） |
| `dice` | 例 `[3, 1]`。指定すると最善手の候補（上位5つ）も返す |
| `cube_value` | キューブの数 1, 2, 4, …, 64（既定 1 = 中央） |
| `cube_owner` | キューブの持ち主 `"white"` / `"black"`、中央なら `null`（既定）。数が 2 以上なら持ち主が要る |
| `doubled` | `true` なら、`on_roll` の側が今 `cube_value` にダブルし、`cube_owner`（相手側）がテイクかパスかを決めるところ（ダイスとは一緒に使えない） |
| `match_length` | マッチの長さ（ポイント）1〜64。0（既定）はアンリミテッド |
| `score_white` / `score_black` | マッチのスコア 0〜`match_length` − 1（既定 0）。アンリミテッドでは 0 だけ |
| `crawford` | `true` ならクロフォードのゲーム（ダブルできない）。片方だけが残り 1 ポイントのときだけ使え、キューブは中央の 1 にする |
| `bottom_colour` | white の駒の色。`1` なら明るい方、`0` なら暗い方。`summary` の文で、明るい方の側を「白」、暗い方を「黒」と呼ぶのに使う（TODO-086）。省略すると white を「白」と呼ぶ |

```
curl -s localhost:8000/analyze -H 'content-type: application/json' \
  -d '{"position_id":"4HPwATDgc/ABMA","dice":[3,1]}'
```

応答（抜粋）:

```json
{
  "position_id": "4HPwATDgc/ABMA", "on_roll": "white", "plies": 2, "game_over": false,
  "pips": {"white": 167, "black": 167, "leader": null, "difference": 0},
  "probabilities": {"white": {"win": 52.5, "gammon": 14.9, "backgammon": 0.7},
                    "black": {"win": 47.5, "gammon": 12.5, "backgammon": 0.5}},
  "equity": {"white": 0.076, "black": -0.076},
  "favourite": "white",
  "moves": [{"move": "8/5 6/5", "steps": [[8, 5], [6, 5]], "equity": 0.16}],
  "summary": "白が有利: 勝率 52.5%（ギャモン 14.9%）、ピップ 白 167 / 黒 167"
}
```

- `moves[].steps` は手をダイス 1 つずつに分けた `[from, to]` の並び（`on_roll` の側から数えたポイント、25 = バー、0 = 上がり）。
- 確率は %、`gammon` / `backgammon` はその側が勝つ場合の内訳（勝率に含まれる）。
- `equity` はキューブなし（cubeless）のエクイティ。+1 が確実なシングル勝ち。マッチでは、gnubg がマッチの勝率から出すアンリミテッドと同じ尺度のエクイティ
  （同じ局面でもスコアで変わる）。最善手の `equity` も同じ。
- `match` はマッチのとき `{"length": 7, "score": {"white": 3, "black": 5}, "crawford": false}`、アンリミテッドでは `null`。
  `summary` の先頭にも「7 ポイントマッチ 白 3 対 黒 5（クロフォード）。」のように入る（白・黒は `bottom_colour` で決まる）。
- `favourite` はエクイティが高い側（マッチでは、このゲームの勝率が高い側）。片方が15個上げ終わっていれば `game_over: true`。
- 駒が15個ずつでない、Position ID が不正、スコアがマッチの長さ以上、クロフォードなのに残り 1 ポイントの側がいないなどは 422 とエラーメッセージ。
- **Luck（`luck`）:** ダイスがあるとき、そのロールの `on_roll` の側の Luck（gnubg と同じ求め方で、キューブなし）。その目で最善手を指したときのエクイティから、
  21 通りの目それぞれの最善手のエクイティを出る確率で平均したものを引く。21 通りの探索は時間がかかるので、`plies` が 2 以上でも 1 手読みで求める。初期局面でゾロ目以外のときは、gnubg と同じく、どちらの側にも出えた 30 通り（ゾロ目以外）で平均する。ダイスがなければ `null`。
- **キューブ判断（`cube`）:** `on_roll` の側がダブル（リダブル）できるなら、振る前の局面で gnubg のキューブ判断を返す
  （アンリミテッドは gnubg の既定どおりジャコビー・ルールあり・ビーバーなし。マッチはスコアどおりでジャコビー・ルールなし。深さは `plies`）。
  ダイスがあるときは、振る前にダブルすべきだった（`double: true`）ときだけ返し、`rolled: true` が付く（TODO-096）。
  相手がキューブを持っているとき、クロフォードのゲーム、gnubg がダブルできないとするとき（クロフォードの後でリードしている側など）は `null`。

  ```json
  "cube": {"question": "double", "doubler": "white", "taker": "black", "value": 1,
           "equity": {"no_double": 0.81, "double_take": 0.899, "double_pass": 1.0},
           "double": true, "too_good": false, "optional": false, "take": true, "proper": "Double, take", "rolled": false}
  ```

  `question` は `"double"`（ダブルすべきか）か `"take"`（`doubled: true` のとき。テイクかパスか）。`value` はダブルする前のキューブの数、
  `equity` はダブルする側から見たキューブありのエクイティ（ダブル前のキューブ 1 つ分を単位とする）。`too_good` はダブルせずギャモンを狙う方がよい局面。`optional` はダブルしてもしなくてもよい局面（gnubg の `Optional double`。マッチで出る）。
  `proper` は gnubg の言葉そのまま。gnubg の Python モジュールにはキューブ判断を返す関数がないので、解析用の子プロセスで gnubg の
  `hint` コマンドを実行し、表示された文字を読んでいる（`engine.py` の `_cube_hint`）。

### `POST /find-corners`（multipart）

フィールド `image`。盤の遊戯面の四隅の推定（`recognizer/corners.py`）を返す:
`{"corners": [[x, y] × 4（左上・右上・右下・左下、送った画像の画素）] または null, "width": 幅, "height": 高さ}`。
PWA は写真を読み込んだ直後に、`/analyze-photo` と同じ大きさに縮めた写真を送り、結果を四隅の初期値にする。
`stream=true` なら NDJSON で、探す段階が終わるたびに `{"stage": "edges", lines: 横の縁の候補 [[端, 端], ...]}`、
`{"stage": "uprights", lines: 縦の縁の候補}`、`{"stage": "candidates", quads: 盤らしい四角形の候補（盤らしい順）}`、
`{"stage": "corners", corners}`（見つかったときだけ）を送り、最後に `{"stage": "done", "result": 上の応答}`（画素はどれも送った画像の画素）。
「もう一度検出」（TODO-068）では、任意のフィールドを足す: `fixed`（JSON の文字列。長さ 4 の配列で、各要素はユーザーが置いた隅の `[x, y]` か `null`）と
`crop`（`"x0,y0,x1,y1"`。その範囲だけを、盤が範囲の大部分を占めてよいものとして探す。PWA はユーザーが切り抜いた画像のとき、画像全体を送る）。
どちらも送った画像の画素で、形が違えば 422。`fixed` の隅はそのまま返り、残りを `crop` の中だけで探す
（固定した隅と合う候補が無ければ `corners` は null）。送らなければ答えは今までと同じ。
`side`（`right` か `left`。TODO-120）を送ると、盤の真横から、手前の人から見て右／左から撮った写真として探す（`recognizer/side.py`）。
四隅の順は同じく手前の人から見た 左上・右上・右下・左下で、右から撮った写真では写真の右上・右下・左下・左上、左から撮った写真では左下・左上・右上・右下になる。
`stream=true` の段階は、長い辺（縦の線）が先なので `uprights`・`edges`（両端）・`candidates`・`corners` の順。`fixed`・`crop` も使える。
空か送らなければ今までと同じ。ほかの値は 422。

### `POST /claude-corners`（multipart）

フィールド `image`。写真を `claude -p` に渡し、Claude に盤の遊戯面の四隅を選ばせる（TODO-082）:
`{"corners": [[x, y] × 4（左上・右上・右下・左下、送った画像の画素。画像の中に収める）], "width": 幅, "height": 高さ}`。
自動の推定（`/find-corners`）が外れる写真のためのもので、PWA の四隅の画面の「Claude に選ばせる」を押したときだけ送る。**押すと写真が Anthropic に送られる。**

- 環境変数 `BG_CLAUDE` に `claude` コマンドのパスを設定したサーバーだけで動く（無ければ 404）。モデルは `BG_CLAUDE_MODEL`（既定 `claude-sonnet-5-5`）
- 写真は長辺 1568px 以下に縮めて JPEG で渡す。ツールは使わせず、利用者の設定や hook も読ませない（`--tools "" --setting-sources ""`）
- 同時に走らせるのは 1 本だけで、走っている間に来たものは待たせず 429
- 60 秒で答えが無ければ子プロセスをグループごと殺して 504。アプリが取り消して接続が切れたときも殺す。
  `claude` が 0 以外で終わった・答えから四隅を読めなかったときは 502

### `POST /analyze-photo`（multipart）

写真から認識（`recognizer/board.py`）して、そのまま解析します。
フィールド: `image`、`corners`（`x1,y1,…,x4,y4`）、`home`（`left`・`right`・`auto`。既定 `right`）、
`bottom_colour`（意味は recognizer/README.md と同じ。既定 `0`。読み取りと、`summary` の白・黒の呼び方（/analyze と同じ）の両方に使う）、`on_roll`、`plies`、`dice`（例 `3,1`。省くと写真から読めたダイスを使う）、`cube_value`・`cube_owner`・`doubled`（/analyze と同じ。ただし `dice` を省いて写真からダイスが読めたときは、`doubled` を false にしてチェッカーの手を評価する）、
`match_length`・`score_white`・`score_black`・`crawford`（/analyze と同じ）、
`keep_corners`（`true` なら四隅を枠や三角形に合わせ直さずに読む。既定 `false`。TODO-084）、
`side`（`right` か `left` なら盤の真横から撮った写真として読む。`corners` は /find-corners と同じ順。空か省くと今までと同じ。TODO-120。`keep_corners` は効かない）、
`stream`（`true` なら下の応答を NDJSON で段階ごとに返す。既定 `false`）。

`stream=true` の応答は `application/x-ndjson` で、1 行に 1 つ、認識の段階が終わるたびに
`{"stage": "fit", corners, columns, bar, by, round}`（四隅の合わせ直し。`by` が `"edges"`（枠の線）で 2 回、`"triangles"`（三角形の並び）で 2 回。`keep_corners=true` では `"corners"` で 1 回だけ。`side` を送ったときは `"side"` で 1 回だけ）、`{"stage": "tips", tips}`、`{"stage": "checkers", corners, columns, bar, checkers}`、
`{"stage": "counts", counts, home, home_guess}`、`{"stage": "dice", dice}`、`{"stage": "cube", cube}`（各値は下の `geometry` と同じ形）が来て、
最後に `{"stage": "done", "result": 下の応答}` が来る。途中で失敗したときは最後が `{"stage": "error", "detail": 理由}`（状態は 200 のまま）。
認識は別のスレッドで動かすので、送り終わるのは認識と解析が終わったとき。

応答は `{"recognized": 認識結果, "home": "left" か "right", "home_guess": {...} か null, "errors": [...], "warnings": [...], "geometry": {...}, "dice_read": [大, 小] か null, "cube_read": {...} か null, "analysis": 上の /analyze と同じ形}`。
盤面は読めたが解析できないとき（クロフォードなのに写真のキューブが片側にある、など）は、`analysis` を `null`、`analysis_error` を理由にして盤面を返す（状態は 200）。
`dice_read` は写真のフィールドに 2 つのダイスがあって、目を自信を持って読めたときだけ入る（recognizer/README.md の「ダイス」）。
`dice` を送らなかったときは、これで最善手も出す。
`cube_read` は写真で見つけたキューブの場所と数字 `{"at": "centre" | "white" | "black" | "field", "value": 2〜64 か null}` か `null`
（recognizer/README.md の「キューブ」「キューブの数字」。`value` は確かに読めたときだけ。真ん中のときは解析で 1 なので常に `null`）。
`cube_value` を送らなかったときは、これで解析する: 片側にあれば数を読んだ数字（読めなければ 2）とし、ダイスが無ければ反対側がダブルしたところとして
テイクかパスかを判定する（`analysis.on_roll` がダブルした側になる）。ダイスがあればその側が持っているキューブとみなす。
`field`（遊戯面の中）なら、`on_roll` の側が読んだ数字（読めなければ 2）にダブルしたところとして相手のテイクかパスかを判定する。このときは
ダイス（写真から読めたものも、送ったものも）を使わず、`dice_read` は `null` にする（TODO-045）。
`home` は読み取りに使った側。`home=auto` のときは駒の並びから推測した側で、`home_guess` に
`{"margin": 尤もらしさの差（正なら右、負なら左。絶対値が 1 未満なら決めずに右）}` が入る。
`geometry` は認識が見つけた遊戯面の位置: `corners`（送った画像の画素で 左上・右上・右下・左下）、
`columns`（12 列の中心、左から。遊戯面の幅に対する割合）、`bar`（バーの左右の端、同じく割合）、
`tips`（見つけた三角形の先 `[x, y]`、画像の画素）、`checkers`（見つけた駒の円 `[x, y, 半径, "white" か "black"]`、画像の画素。
色は近い方の駒の色で、数は数えた結果と一致するとは限らない。読み取り中の演出に使うだけ）、
`dice`（自信をもって読めた盤の中のダイス `[{"quad": 四隅, "value": 目}]`、画像の画素）、
`cube`（見つけたキューブ `{"quad": 四隅, "at": "centre" か "white" か "black" か "field"}` か null）、
`counts`（ポイントとバーで数えた駒 `[{"at": [x, y], "n": 数, "side": "white" か "black"}]`。`at` はポイントの外側の枠の上、バーはバーの上）。
`dice`・`cube`・`counts` も演出に使うだけ。
`warnings` は写真についての注意（日本語の文）。今は、盤を真上から 40° を超えて傾けて撮ったときに「斜めから撮った」と出る（`side` を送ったときは出さない）。
認識で駒数が合わないときは `analysis` が `null` になり、`errors` に理由が入ります（アプリで手修正してから
`/analyze` を呼ぶ想定）。

### `POST /samples`（multipart）

精度改善用に、写真（`image`、JPEG か PNG）と直した後の盤面（`truth`、`static/sample.js` が作る `samples/*.truth.json` の形）を
`BG_SAMPLES_DIR` に `user-<id>.*` として保存する。`id` は端末の中の写真の id（英数字と `-`）で、同じ id は上書き。
`BG_SAMPLES_DIR` を設定していないサーバーでは 404（写真は保存しない）。上限は 1000 組（超えたら 507）。
PWA は盤面の画面の「サーバーに［保存する］」（既定）のときだけ、「解析する」を押すたびに送る。Pi では `bganalyzer.service` が `collected/` に置く（[docs/raspi.md](../docs/raspi.md)）。
保存したあと、前に測ってから新しい組が 10 たまっていれば、`recognizer/collected.py` を子プロセスで起動して測り直し、読み違いの無い古い組を消す（新しい 50 組は残す。結果は `report.md`）。`BG_IMPORT` を設定したサーバー（開発機）では、続けて読み違いのある組を `samples/` に入れて PR をマージまで進める（`recognizer/import_collected.py`）。

### `GET /speech`

`?text=` の 1 文（200 文字まで）を Google 翻訳の読み上げ（`translate_tts`）の声にして、`audio/mpeg` で返す。PWA の「読み上げ」が、読み上げの文を「。」で区切って 1 文ずつ頼む。
Google が断ったり届かなかったりすると 502（PWA はブラウザの音声合成に切り替える）。文は Google に送られる（写真は送らない）。

### `GET /health`

`{"ok": true}` を返す（起動したかの確認用）。

### `GET /version`

```json
{"analyzer": "0.1.0", "recognizer": "0.1.0", "commit": "7bd7f55", "samples": false, "claude": false}
```

`samples` はこのサーバーが `POST /samples` を受けるか（PWA は true のときだけ「サーバーに［保存する］［保存しない］」を出す）。
`claude` は `POST /claude-corners` を受けるか（PWA は true のときだけ「Claude に選ばせる」を出す）。

analyzer（この API と PWA）と recognizer のバージョン、動いているコードの git のコミット ID（取れなければ `null`）。
PWA は画面のいちばん下にこれを出す。上げ方は [CLAUDE.md](../CLAUDE.md) の「バージョン」。

## テスト

```
uv run pytest analyzer
```
