# 局面解析 API（ステップ2）

盤面（gnubg Position ID、または認識結果の `points`）を GNU Backgammon で解析し、
勝率・ギャモン率・バックギャモン率・エクイティ・ピップ数と、どちらが有利かを返す HTTP API です。
PWA（下記）から呼び出します。

GNU Backgammon 本体は PyPI の [`gnubg`](https://pypi.org/project/gnubg/) パッケージ（gnubg のニューラルネットと
ベアオフDBを同梱した Python バインディング）を使います。apt で gnubg を入れる必要はありません。

## 起動

```
uv sync
uv run uvicorn app:app --app-dir analyzer --host 0.0.0.0 --port 8000
```

`--reload` や複数ワーカーは使わないでください。gnubg の拡張モジュールはメインスレッド以外で
1手読み以上の評価をするとクラッシュするため、解析は専用の子プロセス（そのメインスレッド）で行っています。

## PWA（ステップ3）

起動したサーバーの `/` をスマホのブラウザで開くと使えます（`analyzer/static/`、ビルド不要の HTML / JS）。

**作り（0.39.0）:** 画面に出るものはすべて `app.js` の `state` にあり、変えるのは `update(patch)` だけ。
`update` のあとに `render()` が、画面の部分ごとに、出す内容が前と変わった所だけを描き直す（`part(key, draw)`）。
ボタンなどの操作と、サーバーとのやりとり（写真の読み取り・解析）は `update` を呼ぶだけで、画面には直接触らない。
最近の写真（`history.js`）への保存も `state` から自動で行う。描く・計算するファイルは `state` を知らず、渡されたものだけを使う:
`board.js`（盤面のデータと操作）、`board-view.js`（盤面図の SVG）、`corners-view.js`（四隅を合わせる写真）、
`result.js`（結果の表と読み上げの文）、`api.js`（サーバー）、`cube.js`・`moves.js`・`photo.js`・`scan.js`・`sample.js`。
外から確かめるとき（`tools/pi_ui_check.py`）は `window.BgApp`（`state`・`update`・`rolled`）を使う。

**画面を変えずに作りを変えたとき**は、`tools/ui_snapshot.py` で前の版と比べる。クリックだけで 3 つの流れ（手入力・写真・最近の写真）を操作し、
各段階で**見えている**画面（部品の表示、文字、盤面図の SVG、写真の画素のハッシュ、結果、読み上げの文）を記録する。
`record before.json`（前の版のサーバーに向けて）、`record after.json`、`compare before.json after.json` の順で、違いがあれば場所を出して終了コード 1。
2 つの版を並べて動かす手順はファイルの先頭に書いてある。0.39.0 の作り直しは、これで前の版と 52 か所すべて同じことを確かめた。

1. 「うまく読み取るコツ」を読んでから、「写真を撮る」でカメラを開くか、「写真を選ぶ」で端末の写真を選ぶ（アプリ画面のスクリーンショットも可）。「手で入力」で写真なしに初期配置から手入力もできる。
2. 盤の遊戯面の四隅に初期値の点が出る（`/find-corners` で推定。見つからないときは画像の内側の長方形）。
   ずれていればドラッグで合わせる（指の下はルーペで拡大表示）。「四隅をやり直す」で 左上→右上→右下→左下 の順にタップし直すこともできる。
   「範囲を囲む」で写真の上を斜めにドラッグして盤のまわりを囲むと、表示がその範囲に拡大され、その中で四隅を探し直す（盤が写真の中で小さいとき）。
   「範囲を戻す」で写真全体の表示に戻る。「もう一度検出」は、ユーザーが動かした・タップした隅をそのままにして、残りの隅を探し直す。
   囲んだ範囲の外にある隅は、動かしていても探し直す。見つからなければ、動かしていない隅を囲んだ範囲の四隅に置く（囲んでいなければそのまま）。
   手前の人のホーム側（自動/左/右。自動なら駒の並びから推測）と駒の色（暗い方/明るい方）を選んでヘッダーの「盤面を読み取る」。
3. 読み取った盤面が出るので、違うポイントやバーを盤の上で直す（TODO-059）。
   - タップ: 根元から何段目かで、その段まで駒を置く（3 段目なら 3 個）。一番上の駒をタップすると 1 個減る。
     駒が 5 個以上ある所は 5 段目のタップで 1 個ずつ増える。空の所には「空の所に置く色」の色で置く（最後に置いた色に切り替わる）。
     盤の縁のポイントの番号をタップすると空になる。バーは上半分が手前、下半分が奥の駒（どちらも真ん中から外へ積む）
   - 長押し（パソコンは右クリック）: 指のそばに吹き出しが出て、手前／奥と 0〜15 の数を選ぶ。色を間違えた所や数が大きくずれた所に使う
   - 「元に戻す」で手で直した分を 1 つずつ戻せる（写真を読み直したり、色・左右を入れ替えたりすると戻せなくなる）
   駒の色・左右の入れ替えボタンもある。
   ホーム側を自動にしたときは、推測した側をボタンの下に出す（逆なら「左右を入れ替える」）。
   盤の上に転がっている 2 つのダイスが写真から読めたときは、ダイスの目に初期値として入る（「写真からダイスの目を読み取りました」と出るので、違えば直す）。
   読めないとき・自信がないとき（1 つしかない、3 つ以上ある、バーやカップの中など）は空のまま。
   次に振る人とダイスの目（任意。ダイスを入れると、画面の「次に振る人」は「振った人」に変わる。結果の文と読み上げも同じ）、読みの深さ（2手 / 3手。選んだほうを端末に覚える）を選んでヘッダーの「解析する」。ダイスの目が入っているときは、盤面図にもダイスの絵が出る
   （次に振る人の右手側のフィールド、つまり手前なら右・奥なら左に、その人の駒の色で）。
   **キューブ**は場所（中央 / 手前 / 奥）と数を選ぶ（`static/cube.js`。盤面図ではトレイと反対側の端に出る。誰も持っていないときは上下の真ん中、持っているときはその人の側）。写真から場所が読めたときは初期値に入る（遊戯面の中にあれば、次に振る人がダブルしたところとして相手の側に置き、ダイスを消す）
   （「写真からキューブを読み取りました」と出る。数は写真の数字を読む。読めなければ 2。違えば直す）。ダイスがなければ、中央なら次に振る人がダブルすべきかを、
   片側にあれば「その側がダブルされたところ」としてテイクかパスかを判定する（次に振る人はダブルした側に自動で変わる）。
   「ダブルされたところ」を外すと、その側がキューブを持っている扱いになる（持ち主が次に振るならリダブルすべきかを判定）。
   「手番を入れ替える」で次に振る人を反対にできる（解析の結果が出ていれば、そのまま新しい手番で解析し直す）。
4. 解析すると**結果の画面**に移る。上に盤面図（ここでは直せない）、下に勝率・ギャモン率・エクイティ・ピップ数と、ダイスを入れたときは最善手5つ。
   直すときはヘッダーの戻る（スマホの戻るでも）で盤面の画面に戻る。盤面も設定も変えずにもう一度「解析する」を押すと、解析し直さずに同じ結果を出す。
   最善手は盤面図に矢印で出る（最初は 1 位の手。一覧の行をタップするとその手の矢印に変わる。矢印はダイス 1 つにつき 1 本で、「22/15」なら 22→17 と 17→15 の 2 本。途中や行き先でヒットした所は赤い丸。手の表記の読み方は `static/moves.js`）。盤面を直すと矢印は消える。
   写真から読み取ったときは、元の写真も出して読み間違いを見比べられる（下記）。
   ヘッダーの「読み上げ」ボタン（スピーカーの絵と文字。解析したあとに出る。読んでいる間は「■ 止める」で止める）で、最初に、ダイスを入れたときは最善手を、ないときは次に振る人を言い、続けてキューブの判断と形勢（「かなり有利」「ほぼ互角」など）を日本語で手短に読み上げる。勝率やピップ数の細かい数字は読まず、画面にだけ出す（ギャモンの見込みが大きいときとレースの差が 20 ピップ以上のときは一言添える）。結果の表と読み上げの文は `static/result.js` が作る。
   ブラウザ標準の音声合成（Web Speech API）を使うので無料で、サーバーには何も送らない。Android の Chrome では Google の音声になる。

**元の写真の表示（`static/photo.js`）:** 四隅で台形補正した写真を、盤面図と同じ向き・同じポイントの並びで出す。
「並べる」（広い画面では左右、スマホでは上下）と「隠す」を選べる。
写真側のポイントをタップしても同じように直せる。補正には `/analyze-photo` が返す `geometry`
（認識が見つけた盤の四隅と列の位置）を使い、写真の列を盤面図の列にそろえる。補正は端末の中で行い、写真を追加で送ったり保存したりはしない。

**四隅探しと読み取りの途中経過（`static/scan.js`）:** サーバーは段階が終わるたびにその結果を送り（`stream=true`）、
アプリはそれを順に並べて **1 段階ずつ** 写真の上に見せる。どちらも最後の段階を見せ終えたところで完了とする（タップで飛ばせる）。
- **四隅探し**（写真を読み込んだ直後、`/find-corners`）: 写真全体に走査線 → 横の縁の候補の直線（橙）→ 縦の縁の候補の直線（青）→
  盤らしい四角形の候補（黄。いちばん盤らしいものを最後に濃く）→ 四隅（緑）。
  見せ終えたら四隅の点を置く（見つからなければ長方形）。写真をタップすると表示をやめ、すぐ四隅を動かせる
  「もう一度検出」と範囲を囲んだあとも同じ表示で、走査線は囲んだ範囲（囲んでいなければ写真全体）から始まる
- **読み取り**（「盤面を読み取る」）: 四隅から描いた盤の枠・三角形・バーを遠近どおりに重ねて走査線 → 四隅の合わせ直し 4 回
  （枠の線で 2 回、三角形の並びで 2 回。枠が少しずつ寄る）→ 三角形の先 → 駒の円 → ポイントごとの数（とホームの向き）→
  ダイス（四角と目）→ キューブ（四角）。最後のあと、解析がまだならその絵のまま待つ

**写真の上に出す文字は数字だけ**（ポイントごとの数とダイスの目。段階の説明や「見つかりません」などの文字は出さない。ユーザー、2026-10-15）。

**各段階を見せる長さは `scan.js` の `STAGE_MS` の表で、段階ごとに変えられる**（2026-10-16 の時点では、どの段階も 500 ミリ秒。TODO-061）。
段階を一度に受け取ったとき（流さない古いサーバー、途中でまとめてしまう経路）も、同じ順に表の長さずつ見せる。
端末が「視差効果を減らす」（prefers-reduced-motion）なら動かさず、各段階を止まった絵で見せる。
写真の上に描くだけで、読み取りの結果は変えない。

- 読み込んだ写真は、最近の 10 枚まで「最近の写真」に残る（`static/history.js`）。写真を選んだ時点で入り、
  選ぶと盤面を読み取る前の四隅の画面から、指定した四隅・ホーム側・駒の色のまま始まる。読み取って直した盤面も残っていて、
  「前に読み取った盤面を開く」で開ける。残すのは**使っている端末の中（IndexedDB）だけ**で、サーバーには残らない。
  写真は長辺 2048px に縮めて（小さいスクリーンショットはそのまま）保存し、古いものから自動で消える。✕ で 1 枚ずつ消せる。
- 盤面の画面の「精度改善用に書き出す」（`static/sample.js`）は、写真と、手で直した後の盤面を
  `user-日時.jpg` と `user-日時.truth.json`（`samples/*.truth.json` と同じ形）の 2 つのファイルにする。
  共有の画面で送れる端末（iPhone など）では共有の画面が開き、送れない端末（JSON を共有できない Android の Chrome や PC）では 2 つともダウンロードになる。サーバーには何も送らない。
  JSON には認識が読んだ盤面（`read`）と、直したポイントの番号（`fixed_points`）も入る。使い方は TODO-030。
- 長辺 2560px を超える写真は、ブラウザで長辺 2048px に縮めてから送る（この大きさでのサンプルの精度は [recognizer/README.md](../recognizer/README.md) の「精度」の「アプリ経由」の列）。
- 別のホストに PWA を置くときは `?api=https://APIのURL` を付けて開く。
- ホーム画面への追加と Service Worker は HTTPS（または localhost）のときだけ有効。
- **Android** でホーム画面に追加すると、写真アプリなどの「共有」の一覧に BG Analyzer が出る（manifest の `share_target`）。
  共有した写真は Service Worker が端末の中で受け取り（`sw.js`）、選んだときと同じく四隅の指定に進む。サーバーに送るのは「盤面を読み取る」のときだけ。
  Service Worker がまだ動いていないとき（追加した直後など）は、サーバーの `POST /share-target` が写真を読まずにアプリへ戻し、選び直すよう表示する。
  iPhone（Safari）には PWA を共有先にする仕組みがないので、アプリ内で選ぶ。

## API

色の呼び方は認識側と同じです: **white = 写真の手前のプレイヤー、black = 奥のプレイヤー**。

### `POST /analyze`（JSON）

| フィールド | 説明 |
|---|---|
| `position_id` | gnubg Position ID（`board` とどちらか一方） |
| `board` | `{"points": [24個], "bar_white", "bar_black", "off_white", "off_black"}`。`points[i]` は手前側から見たポイント i+1、正 = white、負 = black。off は省略すると 15 − 残りで補完 |
| `on_roll` | 次にサイコロを振る側 `"white"`（既定）/`"black"` |
| `plies` | 読みの深さ 0〜3（既定 2。2 で 1局面 約30ms、3 で 約0.7秒） |
| `dice` | 例 `[3, 1]`。指定すると最善手の候補（上位5つ）も返す |
| `cube_value` | キューブの数 1, 2, 4, …, 64（既定 1 = 中央） |
| `cube_owner` | キューブの持ち主 `"white"` / `"black"`、中央なら `null`（既定）。数が 2 以上なら持ち主が要る |
| `doubled` | `true` なら、`on_roll` の側が今 `cube_value` にダブルし、`cube_owner`（相手側）がテイクかパスかを決めるところ（ダイスとは一緒に使えない） |

```
curl -s localhost:8000/analyze -H 'content-type: application/json' \
  -d '{"position_id":"4HPwATDgc/ABMA","dice":[3,1]}'
```

応答（抜粋）:

```json
{
  "position_id": "4HPwATDgc/ABMA", "on_roll": "white", "plies": 2, "game_over": false,
  "pips": {"white": 167, "black": 167, "leader": null, "difference": 0},
  "probabilities": {"white": {"win": 52.5, "gammon": 14.9, "backgammon": 0.7},
                    "black": {"win": 47.5, "gammon": 12.5, "backgammon": 0.5}},
  "equity": {"white": 0.076, "black": -0.076},
  "favourite": "white",
  "moves": [{"move": "8/5 6/5", "steps": [[8, 5], [6, 5]], "equity": 0.16}],
  "summary": "手前が有利: 勝率 52.5%（ギャモン 14.9%）、ピップ 手前 167 / 奥 167"
}
```

- `moves[].steps` は手をダイス 1 つずつに分けた `[from, to]` の並び（`on_roll` の側から数えたポイント、25 = バー、0 = 上がり）。
- 確率は %、`gammon` / `backgammon` はその側が勝つ場合の内訳（勝率に含まれる）。
- `equity` はキューブなし（cubeless）のマネーゲームのエクイティ。+1 が確実なシングル勝ち。
- `favourite` はエクイティが高い側。片方が15個上げ終わっていれば `game_over: true`。
- 駒が15個ずつでない、Position ID が不正などは 422 とエラーメッセージ。
- **キューブ判断（`cube`）:** ダイスがないとき、`on_roll` の側がダブル（リダブル）できるなら、gnubg のキューブ判断を返す
  （マネーゲーム、gnubg の既定どおりジャコビー・ルールあり・ビーバーなし。深さは `plies`）。ダイスがあるとき、相手がキューブを持っているときは `null`。

  ```json
  "cube": {"question": "double", "doubler": "white", "taker": "black", "value": 1,
           "equity": {"no_double": 0.81, "double_take": 0.899, "double_pass": 1.0},
           "double": true, "too_good": false, "take": true, "proper": "Double, take"}
  ```

  `question` は `"double"`（ダブルすべきか）か `"take"`（`doubled: true` のとき。テイクかパスか）。`value` はダブルする前のキューブの数、
  `equity` はダブルする側から見たキューブありのエクイティ（ダブル前のキューブ 1 つ分を単位とする）。`too_good` はダブルせずギャモンを狙う方がよい局面。
  `proper` は gnubg の言葉そのまま。gnubg の Python モジュールにはキューブ判断を返す関数がないので、解析用の子プロセスで gnubg の
  `hint` コマンドを実行し、表示された文字を読んでいる（`engine.py` の `_cube_hint`）。

### `POST /find-corners`（multipart）

フィールド `image`。盤の遊戯面の四隅の推定（`recognizer/corners.py`）を返す:
`{"corners": [[x, y] × 4（左上・右上・右下・左下、送った画像の画素）] または null, "width": 幅, "height": 高さ}`。
PWA は写真を読み込んだ直後に、`/analyze-photo` と同じ大きさに縮めた写真を送り、結果を四隅の初期値にする。
`stream=true` なら NDJSON で、探す段階が終わるたびに `{"stage": "edges", lines: 横の縁の候補 [[端, 端], ...]}`、
`{"stage": "uprights", lines: 縦の縁の候補}`、`{"stage": "candidates", quads: 盤らしい四角形の候補（盤らしい順）}`、
`{"stage": "corners", corners}`（見つかったときだけ）を送り、最後に `{"stage": "done", "result": 上の応答}`（画素はどれも送った画像の画素）。
「もう一度検出」（TODO-068）では、任意のフィールドを足す: `fixed`（JSON の文字列。長さ 4 の配列で、各要素はユーザーが置いた隅の `[x, y]` か `null`）と
`crop`（`"x0,y0,x1,y1"`。ユーザーが囲んだ範囲）。どちらも送った画像の画素で、形が違えば 422。`fixed` の隅はそのまま返り、残りを `crop` の中だけで探す
（固定した隅と合う候補が無ければ `corners` は null）。送らなければ答えは今までと同じ。

### `POST /analyze-photo`（multipart）

写真から認識（`recognizer/board.py`）して、そのまま解析します。
フィールド: `image`、`corners`（`x1,y1,…,x4,y4`）、`home`（`left`・`right`・`auto`。既定 `right`）、
`bottom_colour`（意味は recognizer/README.md と同じ）、`on_roll`、`plies`、`dice`（例 `3,1`。省くと写真から読めたダイスを使う）、`cube_value`・`cube_owner`・`doubled`（/analyze と同じ。ただし `dice` を省いて写真からダイスが読めたときは、`doubled` を false にしてチェッカーの手を評価する）、
`stream`（`true` なら下の応答を NDJSON で段階ごとに返す。既定 `false`）。

`stream=true` の応答は `application/x-ndjson` で、1 行に 1 つ、認識の段階が終わるたびに
`{"stage": "fit", corners, columns, bar, by, round}`（四隅の合わせ直し。`by` が `"edges"`（枠の線）で 2 回、`"triangles"`（三角形の並び）で 2 回）、`{"stage": "tips", tips}`、`{"stage": "checkers", corners, columns, bar, checkers}`、
`{"stage": "counts", counts, home, home_guess}`、`{"stage": "dice", dice}`、`{"stage": "cube", cube}`（各値は下の `geometry` と同じ形）が来て、
最後に `{"stage": "done", "result": 下の応答}` が来る。途中で失敗したときは最後が `{"stage": "error", "detail": 理由}`（状態は 200 のまま）。
認識は別のスレッドで動かすので、送り終わるのは認識と解析が終わったとき。

応答は `{"recognized": 認識結果, "home": "left" か "right", "home_guess": {...} か null, "errors": [...], "warnings": [...], "geometry": {...}, "dice_read": [大, 小] か null, "cube_read": {...} か null, "analysis": 上の /analyze と同じ形}`。
`dice_read` は写真のフィールドに 2 つのダイスがあって、目を自信を持って読めたときだけ入る（recognizer/README.md の「ダイス」）。
`dice` を送らなかったときは、これで最善手も出す。
`cube_read` は写真で見つけたキューブの場所と数字 `{"at": "centre" | "white" | "black" | "field", "value": 2〜64 か null}` か `null`
（recognizer/README.md の「キューブ」「キューブの数字」。`value` は確かに読めたときだけ。真ん中のときは解析で 1 なので常に `null`）。
`cube_value` を送らなかったときは、これで解析する: 片側にあれば数を読んだ数字（読めなければ 2）とし、ダイスが無ければ反対側がダブルしたところとして
テイクかパスかを判定する（`analysis.on_roll` がダブルした側になる）。ダイスがあればその側が持っているキューブとみなす。
`field`（遊戯面の中）なら、`on_roll` の側が読んだ数字（読めなければ 2）にダブルしたところとして相手のテイクかパスかを判定する。このときは
ダイス（写真から読めたものも、送ったものも）を使わず、`dice_read` は `null` にする（TODO-045）。
`home` は読み取りに使った側。`home=auto` のときは駒の並びから推測した側で、`home_guess` に
`{"margin": 尤もらしさの差（正なら右、負なら左。絶対値が 1 未満なら決めずに右）}` が入る。
`geometry` は認識が見つけた遊戯面の位置: `corners`（送った画像の画素で 左上・右上・右下・左下）、
`columns`（12 列の中心、左から。遊戯面の幅に対する割合）、`bar`（バーの左右の端、同じく割合）、
`tips`（見つけた三角形の先 `[x, y]`、画像の画素）、`checkers`（見つけた駒の円 `[x, y, 半径, "white" か "black"]`、画像の画素。
色は近い方の駒の色で、数は数えた結果と一致するとは限らない。読み取り中の演出に使うだけ）、
`dice`（自信をもって読めた盤の中のダイス `[{"quad": 四隅, "value": 目}]`、画像の画素）、
`cube`（見つけたキューブ `{"quad": 四隅, "at": "centre" か "white" か "black" か "field"}` か null）、
`counts`（ポイントとバーで数えた駒 `[{"at": [x, y], "n": 数, "side": "white" か "black"}]`。`at` はポイントの外側の枠の上、バーはバーの上）。
`dice`・`cube`・`counts` も演出に使うだけ。
`warnings` は写真についての注意（日本語の文）。今は、盤を真上から 40° を超えて傾けて撮ったときに「斜めから撮った」と出る。
認識で駒数が合わないときは `analysis` が `null` になり、`errors` に理由が入ります（アプリで手修正してから
`/analyze` を呼ぶ想定）。

### `POST /samples`（multipart）

精度改善用に、写真（`image`、JPEG か PNG）と直した後の盤面（`truth`、`static/sample.js` が作る `samples/*.truth.json` の形）を
`BG_SAMPLES_DIR` に `user-<id>.*` として保存する。`id` は端末の中の写真の id（英数字と `-`）で、同じ id は上書き。
`BG_SAMPLES_DIR` を設定していないサーバーでは 404（写真は保存しない）。上限は 1000 組（超えたら 507）。
PWA は設定の「Pi に残す」がオンのときだけ、「解析する」を押すたびに送る。Pi では `bganalyzer.service` が `collected/` に置く（[docs/raspi.md](../docs/raspi.md)）。
保存したあと、前に測ってから新しい組が 10 たまっていれば、`recognizer/collected.py` を子プロセスで起動して測り直し、読み違いの無い古い組を消す（新しい 50 組は残す。結果は `report.md`）。

### `GET /health`

`{"ok": true}` を返す（起動したかの確認用）。

### `GET /version`

```json
{"analyzer": "0.1.0", "recognizer": "0.1.0", "commit": "7bd7f55", "samples": false}
```

`samples` はこのサーバーが `POST /samples` を受けるか（PWA は true のときだけ「Pi に残す」を出す）。

analyzer（この API と PWA）と recognizer のバージョン、動いているコードの git のコミット ID（取れなければ `null`）。
PWA は画面のいちばん下にこれを出す。上げ方は [CLAUDE.md](../CLAUDE.md) の「バージョン」。
